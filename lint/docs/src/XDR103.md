## What it reports

Bytes or a string that a submitter or a contract controls reach text storage without UTF-8 and NUL handling.

Sources are `xdr.Memo.Text` and its accessors, `ingest.LedgerTransaction.Memo()`, `xdr.ScVal.Str`,
`ScVal.ExecutableTag`, `ContractExecutableExternalRef.Tag`, `ScBytes`, `ManageDataOp.DataValue`,
`DataEntry.DataValue` and the text arm of a token transfer `MuxedInfo`. Text sinks are the arguments of
`database/sql` and `pgx` `Exec`, `Query` and `CopyFrom`, `string` struct fields tagged `db:"…"`, proto3 string
fields of the reader's own message types, and any field named in `sinkstext` (all errors), and `string` fields
tagged `json:"…"` (a warning: `encoding/json` writes invalid UTF-8 as U+FFFD and NUL as `\u0000`, so the
stored text silently differs from the bytes on chain, and a PostgreSQL `jsonb` column rejects the NUL).

Not sources: `SetOptionsOp.HomeDomain` and `ManageDataOp.DataName`, which stellar-core validates as printable
ASCII. `ScSymbol` is restricted by the host.

The report is silent after a dominating `utf8.ValidString` check together with a NUL check, after
`strings.ToValidUTF8` with NUL stripping, after base64 or hex encoding, after conversion to `[]byte` for a bytes
column, or after a configured sanitiser (`sanitizerstext`). A value that parsed as an integer
(`strconv.ParseUint`, `ParseInt`, `Atoi` with a nil error) or that a dominating comparison or `switch` fixed to
one of a few clean string literals carries no text either.

## Why it matters

A text memo has only an XDR length bound: stellar-core accepts a memo that is not valid UTF-8 and copies it
verbatim into the transaction's events. An `ScString` is arbitrary bytes. PostgreSQL rejects invalid UTF-8 and
NUL in text columns, so one such value fails the whole persist transaction; for a reader that commits a ledger
at a time, that stops ingestion.

## Limits

The analyzer cannot see SQL column types: a column that is really `bytea` is reported until it is configured or
the value is converted to `[]byte`. SQL built by string concatenation is not followed. Fields are followed one by
one through struct values and through struct pointers passed to or returned from functions of the same package (a
builder's methods); what a pointer field points to, and a callee's writes through a pointer, are not. A helper of the
same package called at several sites returns at each site only what that site passed in.
