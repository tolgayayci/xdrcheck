## What it reports

A value read from an authorization entry or from invocation arguments reaches a participant sink (or a configured
state-change sink) without corroboration from meta. Sources are the credential addresses of
`SorobanAuthorizationEntry`, delegate addresses, `RootInvocation` and `SubInvocations`, the contract address and
create-contract preimages of a `SorobanAuthorizedFunction`, `InvokeContractArgs.ContractAddress` and `Args`, and
create-contract preimages.

The report is silent when the value is used only as a key into, or compared with, a set built from meta, and the
sink depends on that membership test.

## Why it matters

The host authenticates only the authorization entries a `require_auth` call matched; a successful transaction can
carry any number of others, naming any address. The proof that an address authorised an operation is the nonce
entry the host wrote for it in the meta. A reader that adds every address in the tree lets a submitter write into
anyone's history.

## Limits

An indexer that deliberately keeps "declared, unverified" relations apart from participants should suppress the
report with that reason. The host also requires authorization for some top-level host functions (a deploy from an
address). When the operation's own host function and the authorization tree reach the same sink through a function
value (a callback both paths call), the rule's source is type-based and cannot tell them apart: that report is a
known false positive of the rule, and it is suppressed with a reason that says the path is the operation's own host
function of a successful transaction.
