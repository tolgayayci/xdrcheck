## What it reports

A value read from the topics or data of a contract event reaches a participant sink, or is parsed into an asset
(an `xdr.Asset`, a catalogued asset constructor, a split on `":"`, a configured `sinksmovement` call), at a point
not dominated by a comparison of the event's `ContractId` with an expected contract ID.

The report is silent after `ev.ContractId` is compared with a contract ID derived from the asset and the network
passphrase (`asset.ContractID(passphrase)`, the shape go-stellar-sdk's token transfer processor uses), after a
configured verifier (`sanitizersevent`), and for a sink keyed by the event's contract ID: a configured movement
sink that takes it as an argument, or a configured sink (`sinksparticipant`, `sinksmovement`) called on a builder
that was given it earlier in the chain, such as `b.WithToken(contractID).WithAccount(to)`, directly or through a
variable or a helper that renders the ID. A record kept explicitly "for contract C" is not a claim
about another contract's asset.

## Why it matters

The host fills an event's contract ID from the executing contract; the topics and data are whatever that contract
passes (soroban-env-host v30.0.0, `src/host.rs` and `src/events/mod.rs`). Anyone can deploy a contract that emits
a four-topic `transfer` naming a victim account and a real classic asset. A reader that credits the asset or adds
the named account as a participant lets a stranger write into another user's history.

## Limits

Any argument earlier in the builder chain that carries the emitting contract's ID keys the builder; the rule does
not check which setter took it. Writing the account into a plain participant set beside a keyed builder is still
reported. Verification done in another package is not seen.
