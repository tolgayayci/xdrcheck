## What it reports

A function or closure that recurses, directly or through other functions of the same package, passing a value of a
self-referential xdr type (after dereference, slice element or range element), with no depth bound. The
self-referential types are computed from the loaded `xdr` package: `SorobanAuthorizedInvocation`,
`SorobanDelegateSignature`, the `ScVal` group, `ClaimPredicate` and the `ScSpecTypeDef` group at go-stellar-sdk
v0.9.0. The report is an error when a level merges its children's results (`Union`, `append(x, ys...)`), and a
warning otherwise.

A bound is an integer parameter, receiver field or captured variable that every recursive call changes by a
constant and that is compared with a limit before recursing, leading to a return or break; or a configured budget
method (`budgetmethods`) called and error-checked first.

## Why it matters

The host checks only the authorization entries that a `require_auth` call matched. Unmatched entries, nested
trees included, are never examined, and a transaction carrying them succeeds, so the shape of the tree is the
submitter's choice. In Go the decoder's depth limit (1500 units by default) already bounds how deep a decoded tree
can be, so the cost is not a stack overflow but work in proportion to a tree the submitter shaped, quadratic when
every level merges its children, and no stated policy for a tree deeper than the reader expects.

A bound silences this rule only. A constant bound on a path fed from ledger meta is then examined by XDR207, which
reports it when it is below what stellar-core admits, and the behaviour past the bound by XDR206. A low fixed cap
is never the quiet option.

## Limits

"The walk only runs for successful transactions" is deliberately not a bound. Recursion through interface
dispatch, through `fmt` and `Stringer` (`ScVal.String`), or across packages is not seen. Walkers over structures
that stellar-core bounds itself (`ClaimPredicate`, at most 4 levels) are reported and can be suppressed with that
reason.
