## What it reports

Rows built from meta that does not mean what the row says:

- `LedgerTransaction.GetDiagnosticEvents()`, or a `DiagnosticEvents` field of the SDK's meta and event types,
  feeding rows with no success check (`Successful()`, `TransactionResultCodeTxSuccess`, a variable holding one) in
  the function or in every same-package caller (an error);
- `LedgerTransaction.GetChanges()` or the `TxChangesBefore`/`TxChangesAfter` fields read in a function that works
  on one operation (an integer parameter named like an operation index, or an operation wrapper type) and feeding
  rows (a warning).

Feeding rows means the value, or a value ranged or derived from it, is used in a composite literal, appended,
assigned to a field or map entry, or passed to a same-package function in such a position. Not reported: a
function whose rows record the transaction's success (it, or a same-package function it calls, reads
`Successful()`), and an accessor that copies the events into a `DiagnosticEvents` field.

## Why it matters

A failed Soroban transaction still carries the diagnostic events of the calls that ran before it failed, some with
`InSuccessfulContractCall` set, but the transaction rolled them back. Rows built from them describe transfers that
never happened. `GetChanges()` holds the fee, sequence-number and transaction-level changes as well as every
operation's, so reading it for one operation attributes changes the operation did not make.

## Limits

Callers are followed within the package, up to four levels. Operation scope is read from parameter names and
types.
