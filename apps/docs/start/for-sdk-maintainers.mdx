For maintainers of a Stellar SDK or XDR library in Go, JavaScript, Rust or Python.

## What you get

- A test in your own repository that puts every corpus entry through your decoder on each pull request.
- A job that fails on a new divergence (`NEW-FAILURE`) and on a listed one that is now fixed (`UNEXPECTED-PASS`),
  so the list of known failures only shrinks with real fixes.
- Expected values that come from the bytes and from the pinned oracle, rs-stellar-xdr, never from another SDK. A
  defect found in one SDK becomes a regression test in yours.

A corpus entry is one rare but valid shape: its XDR bytes, the CAP that introduced it and the values a correct
reader decodes. [Read an entry](/start/read-an-entry) walks one field by field.

## Before you start

- A checkout of this repository, and a checkout of your SDK beside it.
- Your SDK's own toolchain and a zstd decoder. The Go, Rust and Python recipes need none of this repository's
  build; the JavaScript recipe installs the npm runner of a corpus release.
- Step 1 and step 5 use the kit's own tools: Linux, [mise](https://mise.jdx.dev) and [rustup](https://rustup.rs)
  ([requirements](/quickstart#requirements)).

## Steps

<Steps>
  <Step title="Run the recipes here, against the pinned SDKs">

    ```sh
    mise install && make toolchain
    make fetch-sdk && make build      # the one networked step, then the tools
    export PATH="$PWD/bin:$PATH"
    make sdk-ci-examples              # the Go, Rust and Python recipes, offline
    ```

    Each recipe runs the corpus through the SDK release pinned in `pins.toml` and compares the result with the
    `expected-failures.txt` beside it. The run passes as committed.

  </Step>
  <Step title="Pick the recipe for your language">

    | Language | Recipe | Loader | Test step |
    |---|---|---|---|
    | Go | `examples/sdk-ci/go` | `packages/go` | `go test` in `xdrcheck/` |
    | Rust | `examples/sdk-ci/rust` | `packages/rust` | `cargo test --manifest-path xdrcheck/Cargo.toml` |
    | Python | `examples/sdk-ci/python` | `packages/python` | `python -m unittest` in `tests/corpus` |
    | JavaScript | `examples/sdk-ci/js` | `packages/npm` | `npx xdrcheck-corpus-run --sdk .` |

  </Step>
  <Step title="Copy it into your repository">

    For Go, from this checkout, with your SDK at `../go-stellar-sdk`:

    ```sh
    mkdir -p ../go-stellar-sdk/xdrcheck ../go-stellar-sdk/.github/workflows
    cp examples/sdk-ci/go/workflow.yml ../go-stellar-sdk/.github/workflows/xdrcheck.yml
    cp examples/sdk-ci/go/go.mod examples/sdk-ci/go/go.sum examples/sdk-ci/go/corpus_test.go \
       examples/sdk-ci/go/expected-failures.txt ../go-stellar-sdk/xdrcheck/
    ```

    Then follow the comments in the copied files: in `go.mod`, replace `github.com/stellar/go-stellar-sdk` with
    `../` and pin the loader by commit; in the workflow, set `XDRCHECK_REPO`, `CORPUS_VERSION` and `CORPUS_SHA256`.
    The header comment of each language's `workflow.yml` says where its files go (`xdrcheck/` for Go, Rust and
    JavaScript; `tests/corpus/` for Python). The workflow downloads one corpus release pinned by version and
    sha256, and stops before reading anything if the archive does not match.

  </Step>
  <Step title="Write, review and commit the expected-failure list">

    `XDRCHECK_CORPUS` names a release archive, an extracted release or a corpus directory. Against the corpus of
    this checkout, when it is the directory `xdrcheck` beside your SDK:

    ```sh
    cd ../go-stellar-sdk/xdrcheck
    XDRCHECK_CORPUS=../../xdrcheck/corpus XDRCHECK_WRITE_EXPECTED_FAILURES=1 go test -count=1 ./...
    XDRCHECK_CORPUS=../../xdrcheck/corpus go test -count=1 ./...
    ```

    The first command writes `expected-failures.txt` from the run; the second checks the run against it. Read each
    line, then commit the list with the pinned corpus version. JavaScript: `--write-expected-failures FILE`.

  </Step>
  <Step title="Test an unreleased branch at every level">

    The recipes judge the bytes only: decode, consume every byte, re-encode identically (Rust and Python also
    compare the SEP-51 JSON). For decoded values, transaction parsing and the `api` operations, point a
    conformance column at your checkout, from this repository:

    ```sh
    xdrcheck conform fetch --columns 'go@v0.9.0' --sdk ../go-stellar-sdk   # network: the checkout's dependencies
    xdrcheck conform build --columns 'go@v0.9.0' --sdk ../go-stellar-sdk
    xdrcheck conform run --columns 'go@v0.9.0' --sdk ../go-stellar-sdk --report out
    ```

    `SUMMARY.md` in the report directory names the checkout. The same works for Rust and Python columns
    ([Add to CI, section 8](/guides/sdk-ci#8-an-unreleased-sdk-branch-xdrcheck-conform-sdk)).

  </Step>
</Steps>

## When the job fails

| Line in the output | Meaning | What to do |
|---|---|---|
| `NEW-FAILURE` | an entry your SDK did not fail before now fails | a regression, or a corpus release with new entries: read the entry (`xdrcheck entry <id>`) and fix the decoder or add the line |
| `UNEXPECTED-PASS` | a listed failure now passes | remove its line in the same change |
| `NEW-UNREAD` | a variant was never read and the list does not name it `unread` | your SDK skipped a type; generate it, or list the variant as `unread` |
| `NOT-RUN` | a listed item the run does not have | a misspelt or stale line: remove it |
| a sha256 mismatch | the downloaded archive is not the pinned one | check the pin against the release's `SHA256SUMS` |

## Limits

- The loaders and the npm runner are not on a package registry. Pin them by commit or vendor them (one file each;
  Go: two).
- The recipes judge conformance level L0 (bytes). The levels above it need `xdrcheck conform` and a driver, which
  exist for Go, JavaScript, Rust and Python only.
- Entries of the `stress` tier are left out of the recipes: they are built to exhaust a reader without limits.
