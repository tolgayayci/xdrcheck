For SDK maintainers and indexer operators who want to know which corpus entries exercise a given CAP or protocol feature, where their bytes come from, and how often the shape occurs on pubnet. Use it to pick the entries to run against your code when you add support for a CAP, or to judge whether a failing entry is a shape your production traffic contains.

## How to use this page

1. Find the row in the [Rows](#rows) table: one row per CAP, per protocol upgrade without a CAP, and per cross-cutting group (`ledger`, `classic`, `xdr-strict`, `limits`, `strkey`, `xdr-json`). Each label links to the row's section (`#cap-46`, `#classic`).
2. The section lists the row's entries. An entry tagged with several CAPs is listed under each of them, so a row can hold entries whose ID is in another group.
3. Run the entries: `xdrcheck entry --cap 40` lists a CAP's entries; `xdrcheck entry ID` shows one entry (tags, variants, expected values, declared divergences); `xdrcheck conform run --entries 'cap-0040/*'` runs an ID group through the SDK columns, and `xdrcheck replay --caps 40` replays a CAP through your adapter ([CLI](/reference/cli)).

How to read an entry's line:

| Column | Meaning |
|---|---|
| Entry | The entry ID; its manifest is `corpus/manifest/<ID>.json` |
| Pattern | The shape the entry holds, from the manifest's `title` |
| Protocol | The protocol that introduced the pattern (`protocol.introduced`), then the protocols the entry's bytes were emitted under |
| Bytes | `captured: <network> <ledger>`: copied unchanged from that network ledger. `local stellar-core`: emitted by stellar-core 30.0.0 on a local standalone node. `stellar-core golden`: imported from stellar-core's `--check-lcm` goldens. `synthetic`: built by a recipe, for a shape stellar-core does not emit or an SDK call that needs no ledger (`SDK call, no ledger`) |

Entries without a CAP number: 143. Their pattern predates CAPs, shipped in a protocol upgrade without a CAP, or is an encoding rule. Such an entry has `caps: []` and a `caps_note` that says why, carries its protocol in `protocol.introduced`, and is listed under the row of its group (`protocol-01` 1, `protocol-02` 1, `protocol-09` 1, `protocol-15` 2, `protocol-29` 1, `ledger` 11, `classic` 97, `xdr-strict` 11, `limits` 2, `strkey` 15, `xdr-json` 1).

Where a union arm is held by only one or two entries, the section has a collapsed table with how often the scan of pubnet history saw that arm, its first and last ledger, and example transactions. A count per entry is on [Mainnet scan](/results/mainnet-scan#prevalence-by-entry).

## How prevalence is joined

The prevalence tables count union arms. A count per entry, from the scan's token table, is on [Mainnet scan](/results/mainnet-scan#prevalence-by-entry); it is the count of the entry's rarest token, not of the arm. For the arms, this page uses one join that is exact:

1. `xdrcheck-corpus coverage --arms --report FILE` walks every committed input, the entries first, and lists per union arm the first three inputs that hold it.
2. An arm is kept when that list is complete for entries (fewer than three labels, or a label that is not an entry), so the entries named are all the entries that hold it.
3. The arm `Type::ARM` is the scan's type-level token `T|arm|Type::ARM`; `xdrcheck-corpus scan locate --summary` gives its occurrences and first and last ledger, and `--limit 3` its first three transactions.

This gives 147 arms, 120 of them seen on pubnet. An arm the scan's token census does not hold is listed as such only when another arm of its union is in the census. An arm that three or more entries hold, or an entry whose pattern is not an arm (a value, a length, an ordering), has no prevalence row.

## What the counts do not say

- The scan reads the public data lake. Its older ledgers were regenerated by a recent stellar-core, so their transaction meta is v4: an arm that only older meta versions carry (such as `TransactionMeta::v2`) is not in the census even where the network once produced it.
- Counts cover pubnet ledgers 2 to 65,505,999 only; Protocol 30 shapes are after that range.
- Counts are occurrences of the arm in the scanned ledgers; examples are the first transactions in ledger order (`ledger:tx`, `tx` in apply order). An arm's count says nothing about any SDK or indexer result.

The data is `corpus/index.json`, `corpus/coverage.json` (the same rows as `corpus/COVERAGE.md`) and `apps/docs/data/cap-prevalence.json`, refreshed by `apps/docs/scripts/cap_prevalence.py` from a locate index. The scan's integrity check and census: [Mainnet scan](/results/mainnet-scan).

3 entries at a nesting-depth limit are listed in `corpus/COVERAGE.md` rather than here.
