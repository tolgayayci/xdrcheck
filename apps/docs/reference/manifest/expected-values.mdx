## 6. Expected values and how they are matched

### 6.1 Three layers

1. **Bytes** — `variants[].blob`. Re-encoding a decoded value must reproduce them (level L0).
2. **Decoded** — `variants[].decoded`: the SEP-51 XDR-JSON the oracle emits at the pinned library version, stored
   exactly as emitted and compared **as a JSON value**, never as text (SEP-51 encoding is canonical, but decoding
   accepts several spellings). Every path in the manifest is an RFC 6901 JSON Pointer into this document.
3. **Semantic expectations** — `expect`, shared by all variants after `${derived.*}` substitution.

`expect.values[]` connects layers 2 and 3: pinpoints `{path, equals, note?}` (`path` and `equals` required; `equals`
is any JSON value). The oracle asserts each against the sidecar during `verify`; conformance drivers at L2 assert the
same paths against their own projection. These are hand-written, so they check the oracle independently of the fact
that it is built on the same library as one of the SDKs under test. Excerpt of
`cap-0038/pool-issuers-order-by-bytes-not-strkey`:

```json
{
  "path": "/v2/tx_set/v1/phases/0/v0/0/txset_comp_txs_maybe_discounted_fee/txs/3/tx/tx/operations/2/body/change_trust/line/pool_share/liquidity_pool_constant_product/asset_a/credit_alphanum4/issuer",
  "equals": "GDRQL6EF772CANMYX55HXMU463OLAX46ZRCPCWS4KVL66ZS4BYA7OYDL",
  "note": "Raw key e305f885…: sorts first as bytes, although its strkey sorts after the other issuer's …"
}
```

**Key-selected pinpoints.** stellar-core writes an operation's ledger-entry changes from an unordered map
(`LedgerTxn::Impl::getChanges`), so the position of one entry's change in a change list differs between runs and
passphrases. A pinpoint can therefore name the array element by its ledger key instead of its index:
`select: {in, key, change?}`, where `in` is a JSON Pointer to an array of `LedgerEntryChange`, `LedgerEntry` or
`LedgerKey` values, `key` is the SEP-51 JSON of the `LedgerKey`, and `change` (one of `created`, `updated`,
`removed`, `state`, `restored`) picks the change type; `path` is then relative to the selected element. Exactly
one element must match: a change whose entry has the key (a `removed` change whose key equals it) and the given
type, a ledger entry with the key, or a key equal to it. An entry has a key when every field of the key's arm is a
field of the entry's `data` arm with the same value (a `config_setting` key matches the entry whose arm is its
`config_setting_id`). Without `change`, a key with both a `state` and an `updated` change in the list matches
twice and fails. Tokens are allowed in `in` and `key`:

```json
{
  "select": {
    "in": "/v2/tx_processing/0/tx_apply_processing/v4/operations/0/changes",
    "key": {"account": {"account_id": "${derived.accounts.P}"}},
    "change": "updated"
  },
  "path": "/updated/data/account/seq_num",
  "equals": "55834574848"
}
```

`verify` resolves the selection in each variant's sidecar before comparing; the conformance orchestrator resolves
it per variant when it loads the corpus, so a driver receives (and the verdict compares at) the plain pointer
`/v2/…/changes/<i>/updated/data/account/seq_num`.

`expect.reject` belongs to negative entries ([§9.3](/reference/manifest/kinds-and-levels#9-3-negative-entries)); `expect.native` to level L3 ([§6.9](#6-9-native-conversion-l3)).

### 6.2 Whole-ledger receipts: `expect.ledger` and `expect.transactions`

`expect.ledger` counts, for the **whole ledger** (TransactionMeta v4 definitions):

| Count | Definition |
|---|---|
| `transactions` | Length of the transaction processing list |
| `operations` | Operations in the envelopes of those transactions (the inner transaction's for fee bumps). A failed transaction's operations count although it has no operation meta |
| `events` | Consensus events: transaction-level plus operation-level events (contract events included). Diagnostic events are never counted. For TransactionMeta v3 the events are those in the Soroban meta |
| `entry_changes` | All ledger-entry changes: fee processing, changes before and after, operation changes, post-apply fee processing, upgrade processing |

Because classic and fee events depend on node flags ([§4.3](/reference/manifest/entry-fields#4-3-meta-versions-and-flag-profile)), `events` is a property of the blob, not of the abstract
ledger. Each counter an adapter provides must equal the expected one.

`expect.transactions[]`, also whole-ledger: `index` (apply order, required), `hash`, `successful` (required),
`result_code` (the transaction result arm as XDR-JSON names it: `tx_success`, `tx_failed`,
`tx_fee_bump_inner_failed`, …), `operation_result_codes` (one per operation, `<operation>.<code>` in XDR-JSON names,
for example `set_options.success`), `fee_charged` (decimal string or `${derived.…}` token), and for fee bumps
`inner_hash`, `inner_successful`, `inner_result_code`. Listing every transaction with its hash and `successful` lets
the harness detect an indexer that silently skips failed transactions; `cap-0038/pool-issuers-order-by-bytes-not-strkey`
lists all 19, three of them `tx_failed`. A reader's transaction is found by hash: an absent hash is `missing`; each of
`successful`, `result_code`, `operation_result_codes` and `fee_charged` must be equal where the reader holds the
field, otherwise `wrong`. Adapters map their indexer's own result label to these names through a fixed table (the
wallet-backend indexer stores `TransactionResultCodeTxSuccess`, as its transcripts in
`evidence/wallet-backend-replay/` show); the observation carries the XDR-JSON name.

### 6.3 Scope and identity

**Transaction scope.**

- Apart from the receipts of [§6.2](#6-2-whole-ledger-receipts-expect-ledger-and-expect-transactions), every fact belongs to one **transaction**: the variant's focus transaction
  (`focus.tx_hash`), or, when an item carries its own `tx_index`, the transaction at that index (resolved to a hash
  through `expect.transactions[].hash`). Facts are located by transaction hash. What a reader holds for *other*
  transactions of the same ledger never affects an entry's result.
- A reader's fact that carries no transaction locator (an indexer that cannot attribute a row to a transaction) is
  in scope only when the ledger has a single transaction. Otherwise it is listed as unattributed evidence and
  neither satisfies nor violates anything.
- Within the transaction, two groups of facts are **ambient** — every transaction causes them whatever its
  operations do: the fee (movement kinds `fee` and `fee_refund`; state-change kind `balance_changed` when a reader
  models balances as state changes) and the sequence-number bump (state-change kind `sequence_bumped`). TTL
  extensions (`ttl_extended`) are ambient too: the Soroban host extends the TTL of entries a call accesses whatever
  the call is for. Ambient facts satisfy an expectation that lists them, and are **never counted as extras**.

**Identity.**

- An account is identified by its **base** address (`G…` account, `C…` contract, `B…` claimable balance, `L…`
  liquidity pool). A muxed ID is extra routing information, never a different account ([§6.5](#6-5-participants)).
- `asset` is `native`, `CODE:ISSUER`, `liquidity_pool:<hex pool id>`, or a contract address. A classic asset and its
  Stellar Asset Contract address under the run's network passphrase are **the same asset**: the consumer computes
  the contract ID from the asset and the network ID itself and accepts either form (the wallet-backend indexer, for
  example, stores the contract address in its token column). Where an entry gives that address under
  `derived.contracts`, `verify` has checked it against the computed one. A contract address that is not the
  computed address of the expected asset is a different asset, whatever its events claim ([§6.7](#6-7-movements-and-routing), M-7).

### 6.4 Presence, extras and exactness

Every comparison yields one **fact result**: `ok`, `missing`, `wrong`, `forbidden_present` or `not_applicable`.

**Comparison is exact everywhere.** Amounts, IDs and counts are compared as decimal strings or integers: no
tolerance, no rounding, no case folding, no prefix matching. **Never compared:** a reader's own row identifiers,
ordering columns and operation identifiers, and any `<key>_as_stored` value ([§6.6](#6-6-state-changes)).

**Presence.**

- A listed item is **required**: a reader that models its kind must hold a matching fact. No candidate → `missing`.
- An item with `only_if: <modelling choice>` is required only of readers whose adapter declares that choice in its
  `describe` answer (`modelling` in `corpus/schema/adapter-protocol.schema.json`). For other readers it cannot be
  `missing`, and a matching fact they report anyway is allowed. The one choice defined in v1 is
  `initial_authorization_separate`: the reader records the authorisation state a trustline is created with as its
  own change, beside the creation.
- Facts of a kind or sub-kind the adapter does not model are `not_applicable` ([§6.10](#6-10-not-applicable-is-not-dropped)).
- An item marked `unverified: "<reason>"` (a `participants.must_include` account, a `state_changes` item or a
  `movements` item) states something the reference extractor cannot derive from the bytes ([§6.11](#6-11-the-reference-extractor)), for example a
  modelling detail no ledger field carries. The author keeps it as documentation; it is `not_applicable` for every
  reader, and the facts it describes still count as accounted under the exactness flags.

**Extras.** A reader may hold more than an entry asserts. Extra facts are ignored unless they hit a must-not fact
(`participants.must_not_include` → `forbidden_present`; a movement with `count: 0` → `wrong`) or fall inside an
exactness scope:

| Flag | Scope | What counts as an extra (→ `wrong`) | What never counts |
|---|---|---|---|
| `participants.exact` | participants of the focus transaction | any participant whose base address is not in `must_include` | — |
| `state_changes_exact` | operation-level state changes of the focus transaction | any state change in scope that matches no listed item | ambient kinds (`balance_changed`, `sequence_bumped`, `ttl_extended`); a fact matching an `only_if` item; kinds the adapter does not model |
| `movements_exact` | value movements of the focus transaction | any movement in scope that matches no listed item, or more records than `count` | `fee`, `fee_refund` |

**Must-not facts need the transaction.** A `must_not_include` item or a `count: 0` movement also holds for a
reader that holds nothing at all. Such a fact is therefore `ok` only when the reader positively holds the
transaction (it is in the reader's transaction list, or some fact the reader provides is located in it); otherwise
it is `not_applicable`. A hit is `forbidden_present` or `wrong` either way. An entry passes only when at least one
fact that is not a must-not fact is `ok`.

All three default to `false`. The exactness flags are the general must-not mechanism ("this transaction created one
trustline and nothing else"). They are not a statement about fees: an indexer that stores the fee as a balance row
passes an entry whose `state_changes_exact` is true. The wallet-backend indexer at its fixed commits stores a fee
debit and an authorisation row beside the expected trustline creation (rows in `evidence/wallet-backend-731/`); under
these rules the fee row is ambient, the authorisation row matches the `only_if` item, and nothing is left over, so it
passes `cap-0073/sac-trust-creates-trustline`.

### 6.5 Participants

`expect.participants` says who the ledger meta shows was affected. Envelope-only claims are never participants.
It has `must_include` (accounts), `must_not_include` (`{address, because}`, both required) and `exact`.

An account is `{address, muxed_id?, on_chain_form?, roles?, unverified?}`:

- `address` (required) is the **base** address.
- `muxed_id` is a decimal string; `on_chain_form` is the address exactly as its on-chain form renders (`M…` or
  `W…` when muxed).
- `roles` explains why the account is a participant. The vocabulary is open (new values are a minor change):

  | Role | The address is |
  |---|---|
  | `source` | the account whose sequence number the transaction moved |
  | `fee_payer` | the account whose balance fee processing decreased |
  | `operation_source` | an operation's own source account |
  | `destination` | an account the transaction created |
  | `signer_owner` | an account whose signers changed |
  | `trustline_owner` | the owner of a trustline that was created, changed or removed |
  | `issuer` | the issuer of an asset the transaction touched |
  | `sponsor` | an account that sponsors a created entry or whose sponsoring count grew |
  | `contract` | a contract whose own entries (instance or data) changed |
  | `authorizer` | the address of a nonce entry the transaction created: its Soroban authorization was used. Nonce entries are bookkeeping, so no state change is recorded for them; the role is the only trace |
  | `liquidity_pool` | the `L…` address of a liquidity pool whose entry was created, changed or removed |
  | `claimable_balance` | the `B…` address of a claimable balance that was created or claimed |
  | `claimant` | an affected account named as a claimant of a claimable balance the transaction created or claimed |
  | `counterparty` | any other affected address. Pools and balances were recorded as `counterparty` before `liquidity_pool` and `claimable_balance` existed; that stays valid, since roles are advisory (P-4) |
- `unverified` (string): see [§6.4](#6-4-presence-extras-and-exactness).

| Rule | Statement |
|---|---|
| P-1 | For every `must_include` item, the reader's participant set for the transaction must contain an item whose **base address** equals `address`. An indexer that normalises to base accounts satisfies this directly (adapter declaration `muxed: base_only`) |
| P-2 | A reader that reports a `muxed_id` for a participant must report the expected `muxed_id` as a decimal string (or an `on_chain_form` equal to the expected `M…`/`W…`); reporting none is acceptable, with one exception. An indexer whose adapter declares that it also stores the muxed alias (`muxed: base_and_alias`) **must** report the expected `muxed_id` when the item states one and is not marked `unverified`: such an ID was read from the ledger by the reference extractor ([§6.11](#6-11-the-reference-extractor)), and a reader that claims to keep aliases and drops it is `wrong`. An item marked `unverified` is `not_applicable` for that comparison. With `muxed: base_only` the muxed ID is never compared |
| P-3 | An indexer that stores **only** the `M…` or `W…` form and cannot return the base address fails P-1 with `wrong` ("identity stored only in muxed form"), not `missing`. The base account must be present; the muxed form may be recorded too, never instead |
| P-4 | Roles are advisory. A reader is not failed for a missing or extra role unless its adapter declares that it models roles |
| P-5 | No item of `must_not_include` may appear, by base address, anywhere in what the reader holds for the transaction: participants, state-change accounts, movement endpoints, stored addresses. A hit is `forbidden_present`, reported with the item's `because`. Typical items: an address named only in an unmatched authorization entry, the destination of a failed transaction, an address fabricated from a memo, an account "credited" by a forged token event. One exception: a movement the entry itself lists in `movements` (an item with a `count` other than 0, `unverified` included) that states the forbidden address exactly as its `from` or `to` is the entry's own statement: a record matching that item in kind, asset, base endpoints and amount is not a hit for that address (M-7). An item that leaves the endpoint unstated, or states only the base of a forbidden muxed address, spares nothing |
| P-6 | With `exact: true`, the reader's set, reduced to base addresses, must equal `must_include` |

Readers differ in whether a called contract is a participant: the wallet-backend indexer recorded the Stellar Asset
Contract's address as one at commit `c152783c` and no longer does at `e967ce8b` (both runs in
`evidence/wallet-backend-731/`). Entries therefore list contracts under `must_include` only when the contract's own
ledger entries changed, and do not set `exact` on contract-call entries.

### 6.6 State changes

`expect.state_changes[]`: `\{kind, account, asset?, signer?, detail?, cause?, only_if?, tx_index?, op_index?,
unverified?\}`, with `kind` and `account` required. `kind` is one of a closed list of 29 (identical to the list in
`corpus/schema/observation.schema.json`): `account_created`, `account_removed`, `balance_changed`,
`trustline_created`, `trustline_removed`, `trustline_flags_changed`, `trustline_limit_changed`, `signer_added`,
`signer_removed`, `signer_changed`, `sponsorship_changed`, `offer_changed`, `liquidity_pool_created`,
`liquidity_pool_removed`, `liquidity_pool_changed`, `claimable_balance_created`, `claimable_balance_claimed`,
`contract_data_changed`, `contract_deployed`, `entry_restored`, `entry_evicted`, `data_entry_changed`,
`thresholds_changed`, `sequence_bumped`, `account_flags_changed`, `home_domain_changed`,
`inflation_destination_changed`, `ttl_extended`, `contract_code_created`.

`account` is the owner of the changed entry. Two kinds of entry have no address of their own, and their changes are
attributed by a fixed rule:

- **Contract code** (`contract_code_created`, `entry_restored` and `ttl_extended` of a contract-code entry): the
  source account of the transaction that caused the change (the account whose sequence number it moved; the inner
  transaction's source for a fee bump). `detail.wasm_hash` names the code.
- **TTL entries** (`ttl_extended`): a TTL entry is keyed by the sha256 of the key of the entry it belongs to. When
  that key is among the keys the transaction touched (its change lists or its Soroban footprint — the hash proves the
  match), a contract-data entry's TTL is its contract's and a contract-code entry's TTL follows the rule above; a TTL
  whose entry is not found is the source's too, with only `key_hash` in `detail`. A TTL extension makes no
  participant, and the kind is ambient ([§6.3](#6-3-scope-and-identity)).

`signer` is `{type, key, payload_hex?, weight?}`: `type` is `ed25519`, `pre_auth_tx`, `hash_x` or
`ed25519_signed_payload`; `key` the canonical strkey (`G…`, `T…`, `X…`, `P…`); `payload_hex` lower-case hex;
`weight` 0–255. `tx_index` defaults to the focus transaction; `op_index` names the operation.

| Rule | Statement |
|---|---|
| S-1 | An expected item is matched by a reader's state change of the same `kind`, in the same transaction, for the same base `account`, and the same `asset` ([§6.3](#6-3-scope-and-identity), either form) when given. No such candidate → `missing` (or nothing, for an `only_if` item whose choice the reader does not declare) |
| S-2 | `signer`, when given, is compared in full: `type`, canonical strkey `key` (decoded by the harness from what the reader stored), `payload_hex`, `weight`. A stored value that is a prefix of the expected one is `wrong`, not a match. For a signer kind the adapter declares, the signer itself is required: a candidate that carries no signer, or a signer without a key, is `wrong`; `type`, `payload_hex` and `weight` are compared where the reader holds them |
| S-3 | `detail` keys are fixed per kind (table below). A stated key is compared only when the reader's fact carries the same key, by exact equality; a differing value is `wrong`. A reader that does not hold the key is not penalised |
| S-4 | `cause` explains a change that is not the obvious operation (`contract-call` for a trustline created by the Stellar Asset Contract). It is never compared with what the reader stored; an adapter's declared out-of-scope rules may select expected items by it ([adapter-protocol.md](/reference/adapter-protocol) §8.1), so state it consistently on every entry that shows the same kind of change |
| S-5 | `state_changes_exact: true`: after all items are matched, every reader state change of the focus transaction that is not ambient, did not match or fail an item, and is of a kind the adapter declares, is `wrong` ("unexpected `<kind>` for `<account>`"). Ambient kinds and facts matching `only_if` items are outside it. Without the flag such changes are ignored |
| S-6 | Never matched: a reader's own row identifiers, ordering columns or operation identifiers. The wallet-backend indexer's own state-change identifier differs between the contract path and an ordinary ChangeTrust for the same kind of change |
| S-7 | `balance_changed` is compared at the granularity of the transaction. The reference extractor states one net change per (transaction, account, asset); a reader may record one row per event or operation instead (one per mint, transfer or path hop), or the reverse. When the expected items and the reader's candidates for one transaction, base account and asset differ in number and no single candidate matches, the sums are compared: the expected `delta`s against the candidates' `delta`s. Equal sums match; different sums are `wrong`, with the two sums as the diff. Where both sides state `balance_after`, some expected value must also be held (the last event's balance is the net row's). When the counts agree, or a `delta` is missing or not an integer on either side, rows are compared one to one as above |

Matching order: for each item, collect the candidates (S-1). A candidate **matches** when every field the item states
and the candidate carries is equal (S-2, S-3). One or more matches → `ok`. For `balance_changed`, candidates that
differ only in `delta` or `balance_after` are then compared by their net (S-7). Candidates but no match → `wrong`,
listing each differing field with expected and observed value. Either way the candidates are *accounted* and are not
extras for S-5.

**One neutral vocabulary for a created trustline.** Whatever created it — a ChangeTrust operation or a Stellar Asset
Contract `trust` call — the facts are:

| Fact | Presence | Why |
|---|---|---|
| `trustline_created` for the owner and asset, `detail` `{balance, limit, flags, authorized, …}` | **required** | It is what the ledger shows: a created trustline entry |
| `trustline_flags_changed` for the same owner and asset, `detail` `{flags, authorized, initial: true}` | `only_if: initial_authorization_separate` | Some readers keep authorisation as its own history stream and record the state the trustline starts in. That is a modelling choice, not a ledger fact, so it is required only of readers that declare it |

`cap-0073/sac-trust-creates-trustline` states exactly these two items and sets `state_changes_exact: true`.

An adapter maps its indexer's model onto these kinds **one row to one fact**; it never merges two of the indexer's
rows into one fact or splits one into two. For the wallet-backend indexer: `TRUSTLINE/ADD` → `trustline_created`;
`BALANCE_AUTHORIZATION/SET` → `trustline_flags_changed` (and the adapter declares `initial_authorization_separate`,
because the indexer writes that row for every new trustline, including ordinary ChangeTrust ones);
`BALANCE/DEBIT` at transaction level → `balance_changed`, ambient.

`flags` is the XDR `TrustLineFlags` bit mask; `authorized` and the two other booleans are its bits spelled out, so an
entry states both and either representation can be matched. On `account_flags_changed`, `flags` and `flags_before`
are the `AccountFlags` bit mask after and before, and `auth_required` (1), `auth_revocable` (2), `auth_immutable` (4)
and `auth_clawback_enabled` (8) are its bits after the change. `home_domain_hex` is the new home domain's bytes in
lower-case hex; `home_domain` and `home_domain_before` are the text after and before, given only where the bytes are
UTF-8 (`""` when empty). `inflation_destination` and `inflation_destination_before` are `G…` addresses; a cleared
destination has `cleared: true` and no `inflation_destination` (the named destination is not a participant: its own
entry did not change). On `ttl_extended`, `key_hash` is the TTL entry's key (hex), `key_xdr_hex` the XDR of the key
it belongs to (so `key_hash` is the sha256 of those bytes), `contract` its contract for contract data, and the
`live_until_ledger` values the ledger sequences after and before. `code_bytes` is the length of the uploaded code. Limits and balances are in the asset's smallest unit.
Where an indexer holds a value in another representation, its adapter reports the literal token under
`<key>_as_stored` and leaves `<key>` out; `_as_stored` values are shown as evidence and are not compared in v1. (The
wallet-backend indexer stores a trustline limit as the decimal `922337203685.4775807` — see
`evidence/wallet-backend-731/README.md` — and, in the ordinary ChangeTrust path only, repeats it on the
authorisation row; that is why no expectation states `limit` on `trustline_flags_changed`.)

### 6.7 Movements and routing

`expect.movements[]`: `{kind, asset, amount, from?, to?, routing?, count?, tx_index?, op_index?}`, with `kind`,
`asset` and `amount` required.

- `kind` ∈ `transfer`, `mint`, `burn`, `clawback`, `fee`, `fee_refund`.
- `asset` as in [§6.3](#6-3-scope-and-identity) (possibly a `${derived.…}` token).
- `amount` is a non-negative decimal string in the asset's smallest unit, or a `${derived.…}` token where it differs
  per variant (the same `trust` call was charged 74541 at Protocol 28 and 34800 at Protocol 30).
- `from`, `to` are accounts ([§6.5](#6-5-participants)).
- `count` (default 1) is how many records a reader must hold for this movement; it pins double-counting bugs.
- `routing` is the event's `to_muxed_id`, typed by `routing.type`: `absent` (key not present), `void` (key present,
  value Void — it occurs on pubnet, emitted by custom token contracts), `u64`, `text`, `bytes`; `routing.value`
  carries the value. stellar-core copies the transaction memo into this field for classic payments to unmuxed
  destinations, so `text` and `bytes` values are chosen by the sender and are never an address. Observed in the
  `evidence/local-core/` run: a payment whose text memo looks like the start of a `G…` address carries that text as
  `to_muxed_id` (`evidence/local-core/out/testnet/run-1/decoded/23-L25.json`), and one with a non-UTF-8 text memo
  carries those bytes (`evidence/local-core/out/testnet/run-1/decoded/24-L26.json`).

| Rule | Statement |
|---|---|
| M-1 | Each expected movement must be matched by exactly `count` reader records with the same kind, asset ([§6.3](#6-3-scope-and-identity)), amount and base `from`/`to`. More records → `wrong`; fewer → `missing`. An amount the adapter reports as `amount_as_stored` must be a plain integer equal to `amount`. A matched item accounts only its matching records: another record with the same kind, asset and endpoints but a different amount or routing is left over, and is an extra under `movements_exact` |
| M-2 | `routing.type` `absent` and `void` both mean "no routing ID": a reader passes with none. A reader that reports a routing value must report the same type and value |
| M-3 | A reader must not turn a `text` or `bytes` routing value into an `M…` address (it would appear as a participant or as `to.on_chain_form`); the entry lists that address under `must_not_include` |
| M-4 | `count: 0` asserts the reader holds no such record (double-count, fabrication and forged-event pins): any record with that kind, asset and base `from`/`to` is `wrong`, whatever its amount or routing |
| M-5 | `movements_exact`: see [§6.4](#6-4-presence-extras-and-exactness). Fee movements are outside it |
| M-6 | Fee movements (`fee`, `fee_refund`) are matched only when listed, and only for adapters that declare the fee movement sub-kinds |
| M-7 | **The emitting contract decides whose movement it is.** A token-shaped event (`transfer`, `mint`, `burn`, `clawback`) is a movement of asset X only when the contract that emitted it **is** X: for a classic asset, the Stellar Asset Contract whose ID derives from that asset and the network ID; for a contract token, that contract's own address. An event from any other contract that merely names a classic asset in its topics is that contract's claim about its own token, and a reader that credits the classic asset from it is wrong. Entries that carry such an event pin it with `count: 0` on the classic asset and a `must_not_include` on the "recipient". A reader that publishes token events per emitting contract may record the event as a movement of the emitter's own token (asset = the emitting contract); the entry allows that with an `unverified` item for that asset, which `must_not_include` does not cover (P-5) |

### 6.8 Addresses

`expect.addresses[]`: `{strkey, type, xdr_bytes?, chars?}` (`strkey` and `type` required) — an address the reader
must be able to store and return unchanged. `type` ∈ `account`, `muxed_account`, `contract`, `muxed_contract`,
`claimable_balance`, `liquidity_pool`, `signed_payload`, `pre_auth_tx`, `hash_x`; `xdr_bytes` and `chars` give its
size. The harness asks the adapter for the stored form, decodes it itself, and compares the full string: the expected
strkey must be the full decoding of at least one stored value in the transaction; a stored value that carries the
same key material but decodes to a different or undecodable address (truncated, wrong type, payload dropped) is
`wrong`. Lengths that break fixed-width columns (SEP-0023): `M…` and `W…` 69 characters, `B…` 58, `P…` 69 to 165.
`cap-0040/signed-payload-signer-added` lists its 69-character `P…` signer (`xdr_bytes` 44).

### 6.9 Native conversion (L3)

`expect.native`: `{map_entries?, on_lossy_conversion?, bytes_preserved?}` — what an SDK's conversion of a value to
the language's native types must preserve. `map_entries` is the number of map entries that must survive;
`on_lossy_conversion` is the acceptable behaviour when the native type cannot hold the value: `error` or
`preserve_all`; `bytes_preserved` says byte values must come through unchanged. The case it was made for: a map
whose keys `1` (u32) and `"1"` (symbol) collide as native keys, which an SDK silently collapsed into one
([js-stellar-sdk#1789](https://github.com/stellar/js-stellar-sdk/issues/1789); reproduction in `evidence/js-1789/`).

### 6.10 "Not applicable" is not "dropped"

An adapter declares, in `describe`, the observation kinds and sub-kinds its indexer models (`supported`,
`subkinds`, and a `reason` when not supported). Expected facts of a kind or sub-kind the adapter does not model are
`not_applicable` and never count against it. An entry whose facts are all `not_applicable`, or whose only `ok` facts
are must-not facts ([§6.4](#6-4-presence-extras-and-exactness)), produces no verdict about that reader. A fact the reader *does* model and does not hold
is `missing`, which is a drop.

### 6.11 The reference extractor

`xdrcheck-corpus extract <entry>` derives participants, state changes and movements from what stellar-core actually
changed, independently of any reader under test, and `verify` requires it to agree with the author's `expect`
([§11](/reference/manifest/checks-and-versioning#11-checks-beyond-the-json-schema), check 8). Its rules, summarised:

- **Sources and their standing.** It reads ledger-entry changes (fee processing, changes before and after, operation
  changes, Soroban changes — written by core from real state deltas) and consensus events. Classic and fee events are
  a flag-dependent convenience view and are cross-checked, not trusted alone. Diagnostic events are non-consensus and
  attacker-influenced and are **never** read. The envelope is used for two things only: to label a change's `cause`
  with the operation type, and to attach a muxed alias to a participant the meta already established. It never adds
  a participant from the envelope.
- **Per transaction, in apply order.** The fee: in fee processing, the account whose balance decreased is the fee
  payer and the decrease is a `fee` movement; an increase in post-apply fee processing is a `fee_refund`. The outcome:
  successful iff the result arm is `tx_success` or `tx_fee_bump_inner_success`. Transaction-level changes: the
  account whose sequence number changed is the source; one-time signer removals are `signer_removed`. A **failed**
  transaction stops here: its participants are the fee payer and the source only, and every other address in its
  envelope is proposed as a `must_not_include` candidate.
- **Operation changes** (successful transactions): each change is classified by entry type and transition into the
  state-change kinds of [§6.6](#6-6-state-changes); the owner of each changed entry becomes a participant with a role from the entry type
  ([§6.5](#6-5-participants): a pool's or balance's own address is `liquidity_pool` / `claimable_balance`, an affected claimant of a
  balance created or claimed is `claimant`); a classic entry changed under an InvokeHostFunction operation gets
  `cause: contract-call`. Contract code and TTL entries are attributed as [§6.6](#6-6-state-changes) says; a TTL extension adds no
  participant.
- **Events**: a token-shaped event yields a movement keyed on the contract that emitted it (M-7). If the emitter is
  the Stellar Asset Contract of a classic asset touched by the transaction (or of the native asset), the movement's
  asset is that classic asset; otherwise it is the emitting contract's own token, creates no classic balance fact,
  and an event that names a classic asset anyway is flagged as a forged asset claim with proposed `count: 0` and
  `must_not_include` facts. Only a `u64` routing value sets `to.muxed_id`, and it also attaches that muxed ID (and
  its `M…` form) to the participant as an alias, as the envelope's MuxedAccounts do.
- **Soroban authorization**: a created nonce entry proves that an address authenticated (role `authorizer`; no state
  change is recorded for the nonce entry). An
  address that appears only in authorization entries, with no nonce and no changed entry, is a `must_not_include`
  candidate: a Stellar Asset Contract transfer carrying unmatched authorization entries with void signatures still
  succeeded in the `evidence/local-core/` run (driver step `h:SAC-transfer-with-unmatched-auth`, ledger 30,
  `evidence/local-core/out/testnet/run-1/decoded/28-L30.json`).
- **No classic events in the blob** (a flag profile without them, or an old lake object without backfilled events):
  classic movements are derived from balance deltas per operation instead, and `movements_exact` is set only on the
  event basis.

The extractor proposes; the author decides; `verify` fails on any disagreement until the author resolves it by
reading the bytes again. Agreement means every value the author states is one the extractor derives, and equal:

- a participant's stated `muxed_id` or `on_chain_form`, a state change's stated `detail` key, and a movement
  endpoint's stated `muxed_id` must each be derived by the extractor with the same value — a stated value it does not
  derive is a disagreement, not a skip;
- an `only_if: initial_authorization_separate` item is confirmed against the `trustline_created` of the same
  transaction, account and asset: its `flags`, `authorized`, `authorized_to_maintain_liabilities` and
  `clawback_enabled` must equal the created trustline's, and `initial` must be `true`;
- roles are not compared (P-4);
- an item the author marks `unverified: "<reason>"` ([§6.4](#6-4-presence-extras-and-exactness)) is not required — the honest way to keep a value no
  ledger field carries. Its facts still count as accounted under the exactness flags.
