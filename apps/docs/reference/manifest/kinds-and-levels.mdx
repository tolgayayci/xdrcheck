## 9. `api`, `strkey` and negative entries

### 9.1 `api`

No blob. `api` is `{op, input, expect_xdr_hex?, expect_value?, expect_reject?}` with `op` and `input` required.

- `op` is an SDK-neutral name from a closed list, which each driver maps to its SDK's function: `asset.compare`,
  `liquidity_pool.id`, `liquidity_pool.asset`, `muxed_account.encode`, `muxed_account.decode`, `offer.manage_sell`,
  `offer.manage_buy`, `scval.from_native`, `scval.to_native`, `scval.sort_map`, `strkey.encode`, `strkey.decode`,
  `transaction.parse`, `transaction.hash`, `memo.text_roundtrip`, `address.to_strkey`, `address.from_sc_address`,
  `signer_key.to_strkey`, `scval.native_roundtrip`, `operation.object_roundtrip`, `xdrjson.decode`,
  `asset.from_operation`, `price.encode`, `xdr.custom_union_encode`. The list is the schema's `$defs/apiOp`, which the
  driver protocol schema references; it grows only with a schema minor version.
- `input` holds the arguments by name. An argument that must reach the SDK in a language-native numeric type is
  written `{"native": "number", "value": "…"}`, bytes as `{"hex": "…"}`, everything else as a string. Strings may
  contain `${derived.*}` tokens.
- `expect_xdr_hex` (lower-case hex), `expect_value` (any JSON value) or `expect_reject` (boolean) state the result.
  When `expect_reject: true` is given **together with** `expect_xdr_hex` or `expect_value`, either outcome conforms —
  the exact result, or a refusal ("exact or refuse").

Example: `\{"op": "offer.manage_sell", "input": \{"offer_id": \{"native": "number", "value": "9007199254740993"\}\},
"expect_reject": true\}`. The defect it pins
([js-stellar-sdk#1785](https://github.com/stellar/js-stellar-sdk/issues/1785)) is that the pre-fix SDK accepts a
number that is not a safe integer: the driver, building that JavaScript number, has already lost the last digit, and
the SDK then encodes …992 (reproduction in `evidence/js-1785/`). Shapes stellar-core rejects at submission, such as a
pool trustline with its assets in strkey order (rejected in the `evidence/local-core/` run, step
`e:pool-trust-WRONG-order` in `evidence/local-core/out/testnet/run-1/driver.json`), can never be core-emitted and are `api` entries or
synthetic negatives.

### 9.2 `strkey`

`strkey` is `{text, type?, payload_hex?, origin?}` with `text` required. `type` ∈ `account`, `muxed_account`,
`secret_seed`, `pre_auth_tx`, `hash_x`, `signed_payload`, `contract`, `muxed_contract`, `liquidity_pool`,
`claimable_balance`; `payload_hex` is the decoded payload; `origin` names the published document and vector label
(for example "SEP-0023 v1.4.0 invalid #15"). Invalid vectors carry `expect.reject`. The 30 published SEP-0023 v1.4.0
vectors are entries of the family `strkey/sep-0023-v1.4.0-vectors`.

### 9.3 Negative entries

`negative: true`, `synthetic: true`, and `expect.reject` = `{reason, note?, limits?}` with `reason` from a closed list:

| Class | Reasons |
|---|---|
| XDR strictness | `nonzero_padding`, `bool_range`, `optional_flag_range`, `enum_undeclared`, `union_arm_undeclared`, `length_exceeds_max`, `length_exceeds_input`, `trailing_bytes`, `depth`, `record_mark` |
| Strkey | `strkey_checksum`, `strkey_length`, `strkey_version`, `strkey_padding`, `strkey_noncanonical` |
| API | `value_out_of_range`, `ordering` |

A vector "one level beyond reader X's limit" is therefore accepted by the oracle unless the entry states X's boundary as `expect.reject.limits` = `{depth}` (an integer ≥ 1, in stellar-xdr units); the `reject` check then decodes at that depth.

**Record-mark vectors.** A vector whose fault is in the RFC 5531 record marks (the last-fragment bit clear, a mark
that declares more bytes than remain, a mark shorter or longer than its record's value) sets `framing:
"record-marked"` and `frame_index` on its variant ([§4.2](/reference/manifest/entry-fields#4-2-variants)) and `reason: "record_mark"`. Its blob is the stream. The
oracle reads every mark of the stream — a mark fault anywhere rejects it — and decodes record `frame_index`, which
must hold exactly one value of `xdr_type`; a declared length that disagrees with that value is a mark fault too.
Conformance drivers receive the same input as `framing: "record-marked"` with `frame_index` (driver protocol). The
oracle's reason classes: a clear last-fragment bit is `record_mark`; a mark past the end of the stream, or shorter
than its value, is `record_mark` or `length_exceeds_input`; a mark longer than its value is `record_mark` or
`trailing_bytes`.

An "undeclared" vector must use a value that no pinned XDR definition declares: `SCVal` type 22 is
`SCV_EXECUTABLE_TAG` at Protocol 30, so undeclared-discriminant vectors use 23 or above. The two "undeclared" reasons
differ in practice: stellar-core's own decoder rejects an undeclared **union discriminant** but accepts an undeclared
value in a **plain enum field**, so `enum_undeclared` entries carry a `core_behaviour` block saying stellar-core
accepts. Observed with `stellar-core print-xdr` v30.0.0, one transcript per input:
`evidence/core-print-xdr/out/union-undeclared-scvaltype.txt` (rejected), `evidence/core-print-xdr/out/enum-undeclared-durability.txt` (accepted) and
`evidence/core-print-xdr/out/scv-executable-tag-22.txt` (type 22 decodes). The same folder shows it rejects non-zero padding
(`evidence/core-print-xdr/out/bytes-pad-nonzero.txt`), an optional flag of 2 (`evidence/core-print-xdr/out/optional-flag-2.txt`), trailing bytes
(`evidence/core-print-xdr/out/trailing-1.txt`) and over-long vectors (`evidence/core-print-xdr/out/signers-21.txt`).

A negative entry is never served to an indexer as a ledger. Where implementations legitimately differ — stellar-core's
own decoder reads a boolean of 2 as true (`evidence/core-print-xdr/out/bool-2.txt`) while the XDR rule admits only 0
and 1 (probe vector 6a of `evidence/sdk-matrix`) — the entry says so in `why`, and the divergence matrix reports the
split rather than a single verdict.

### 9.4 `spec`: contract interfaces

A `spec` entry is a contract interface (SEP-48): an `SCSpecEntry` stream with no frame between entries, held by a
Wasm module in its `contractspecv0` custom sections, or bare. Its one variant has `xdr_type: "SCSpecEntry"` and
`container`: `wasm` (the blob is the module, `blobs/<aa>/<sha256>.wasm`) or `xdr-stream` (the blob is the stream,
`.xdr`). Code read from a network carries `source.kind: "contract-code"` with the `network`, the `wasm_hash` (the
blob's sha256), the `upload_ledger` (the CONTRACT_CODE entry's last-modified ledger), how it was fetched and when;
synthetic interfaces are built by `xdrcheck-corpus synth` from a `spec` recipe (SEP-51 JSON of each entry, encoded by
the oracle, then byte edits for the vectors the oracle refuses to encode).

`expect.spec` is read from the bytes by the corpus's own section reader (`xdrcheck_xdr::spec`) and written by
`xdrcheck-corpus render`; `verify --checks spec` reads the bytes again and fails on any difference:

| Field | Meaning |
|---|---|
| `sections` | `contractspecv0` custom sections in the module (Wasm only), names compared as raw bytes |
| `entries` | every whole entry, in stream order across all sections: `kind` (`function`, `struct`, `union`, `enum`, `error_enum`, `event`), `name`, `args` (`{name, type}` for function inputs, struct fields, union and enum cases, event params) and, for a function, `outputs` |
| `clean_end` | every section decodes to whole entries with nothing left over |

Types are written `u32`, `option<T>`, `result<T,E>`, `vec<T>`, `map<K,V>`, `tuple<A,B>`, `bytes_n<N>`,
`udt:<name>`; a union case's type is `void` or `tuple<…>`, an enum case's `=<value>`, an event param's
`<type>@topic_list` or `<type>@data`. SEP-48 stores an interface in **one** section, so an entry with more than
one section or a stream that does not end cleanly is negative (`expect.reject.reason` `spec_sections`,
`length_exceeds_input`, `trailing_bytes` or `length_exceeds_max`). A module with no spec section is a positive
entry with `sections: 0` and no entries: a reader may return an empty interface or report the absence as an
error, and both conform. `xdrcheck-corpus coverage --arms --universe SCSpecEntry` counts the `SCSpecEntry` arms the
spec entries reach.

### 9.5 Validity and flags: the negative-case vocabulary

Every entry states what a correct reader does with its input, in the vocabulary of the WebAssembly spec tests
(`malformed` against `invalid`) and Wycheproof (`valid`, `invalid`, `acceptable`, with bug-class flags):

| `validity` | Meaning | Entries today |
|---|---|---|
| `valid` | The input decodes and is accepted. Every ledger stellar-core wrote is valid | every `ledger` entry, positive `xdr`, `spec` and `strkey` entries, `api` calls with an exact result |
| `malformed` | The bytes (or text) must fail to decode: a decoder that returns a value is wrong | negative entries whose `expect.reject.reason` is a decoding rule (XDR strictness, strkey, spec sections cut short or with bytes left over); `api` refusals of a parse or decode call |
| `invalid` | The input decodes, and a validating reader must reject it | negative entries whose reason is `value_out_of_range`, `ordering` or `spec_sections`; `api` calls that must be refused on their arguments |
| `acceptable` | A reader may accept or reject, and both conform | `api` entries with `expect_reject` together with an exact result ("exact or refuse", [§9.1](#9-1-api)) |

The schema ties `validity` to the other fields, so the two can never disagree: `negative: true` means `malformed`
or `invalid`, and a `malformed` or `invalid` entry of kind `ledger`, `xdr`, `spec` or `strkey` is `negative`;
`expect.reject.reason` `value_out_of_range`, `ordering` or `spec_sections` means `invalid`, any other reason
`malformed`; an `api` entry with `expect_reject` and an exact result is `acceptable`, with `expect_reject` alone
`malformed` or `invalid`, and without `expect_reject` `valid`. A variant may state its own `validity` when it
differs from the entry's; none does today.

`flags` names the bug classes, from a closed list. Every reject reason of [§9.3](#9-3-negative-entries) has the flag of the same name in
kebab case (`trailing_bytes` → `trailing-bytes`), and an entry with an `expect.reject.reason` carries that flag.
Further flags:

| Flag | Meaning |
|---|---|
| `core-lenient` | stellar-core's own decoder accepts the input (`core_behaviour.accepts: true`); set exactly then |
| `depth` | also on valid entries: nesting at or right below a depth limit (`limits/`) |
| `discriminant-type` | a union switched on a type XDR does not allow as a discriminant |
| `native-number-precision` | an integer passed as a language-native number that cannot hold it exactly (2^53 + 1) |
| `non-utf8-text` | text fields holding bytes that are not UTF-8 |

How a runner reads it: `valid` — decode (and, for `api`, the call) must succeed with the expected value;
`malformed` — the decoder must refuse the input (level L0); `invalid` — decoding may succeed, and the reader's
validating layer (object parse, API call) must refuse it; `acceptable` — either outcome conforms, but a returned
value must be the stated one. A reader that accepts a `malformed` or `invalid` input has the known-divergence
outcome `accepts_invalid` ([§7](/reference/manifest/divergences-and-replay#7-known-divergences)).

## 10. Conformance levels by kind

`conformance.levels` lists which levels apply: L0 codec round-trip, L1 SDK object parse, L2 decoded values, L3
native conversion, L4 API call, `spec` the SDK's contract-spec reader, and `json` the XDR-JSON converters
(SEP-51: XDR to JSON, the JSON against the converter's own schema, JSON back to XDR;
[conformance-protocol.md](/reference/driver-protocol#conformance-rules) §2a).

| Kind | L0 | L1 | L2 | L3 | L4 | spec | json |
|---|---|---|---|---|---|---|---|
| `ledger` | decode and re-encode the `LedgerCloseMeta` | parse **every transaction envelope in the transaction set** through the SDK's transaction object, and read the ledger through the SDK's ledger reader where one exists | `expect.values` against the driver's projection | where `expect.native` exists | — | — | every positive variant, on the XDR-JSON columns |
| `xdr` | decode and re-encode the value | the SDK object for that type, if any | as above | as above | — | — | as above |
| `api` | — | — | — | — | the call | — | — |
| `strkey` | — | — | — | — | decode / encode | — | — |
| `spec` | — | — | — | — | — | the SDK's spec reader on the Wasm or stream: its entries against `expect.spec` | — |

The L1 rule for `ledger` entries is why `cap-0038/pool-issuers-order-by-bytes-not-strkey` is a single ledger entry
and needs no separate envelope slice: the defect shows when the SDK builds its transaction object from the envelope,
while the raw XDR codec round-trips it on every version tested (`evidence/js-1766/transcript-prefix.txt`; the
other SDKs as probe vectors 1a–1f of `evidence/sdk-matrix`).

### 10.1 `derived.l1`: what the object layer must read

`variants[].derived.l1` holds the values an SDK's object layer reads from the variant's **focus**, computed by
`verify` with the oracle; a driver reports the same keys at L1 and the runner compares them with these, and only
these. The key list is closed and every value is a string:

| Key | Value | Implied when |
|---|---|---|
| `memo_type` | `none`, `text`, `id`, `hash` or `return`: the focus transaction's memo arm (the inner transaction's for a fee bump) | there is a focus transaction |
| `operation_type` | the focus operation body's XDR-JSON snake_case arm, for example `change_trust` | there is a focus operation |
| `operation_source` | the focus operation's own source as it is on chain (`G…`, or `M…` when muxed) | the operation has a source |
| `address` | the operation's counterpart account as it is on chain: `destination` of `create_account`, `payment` and both path payments; the `account_merge` destination; `trustor` of `allow_trust` and `set_trust_line_flags`; `from` of `clawback`; `sponsored_id` of `begin_sponsoring_future_reserves` | for those operation types |
| `muxed_id` | the muxed ID (decimal) of `address`, else of `operation_source` | one of them is muxed |
| `asset` | `native` or `CODE:ISSUER`: `asset` of `payment`, `set_trust_line_flags`, `clawback` and `create_claimable_balance`; `dest_asset` of both path payments; the `change_trust` line unless it is a pool share | for those operation types |
| `pool_id` | lower-case hex: the sha256 of a pool-share `change_trust` line's `LiquidityPoolParameters` XDR; `liquidity_pool_id` of `liquidity_pool_deposit` and `liquidity_pool_withdraw` | for those operation types |
| `offer_id` | decimal: `offer_id` of `manage_sell_offer` and `manage_buy_offer` (`0` for a new offer) | for those operation types |

The focus is: for a `ledger` variant, the transaction at `focus.tx_index` (found by its hash under the variant's
passphrase) and, when `focus.op_index` is given, that operation; for an `xdr` variant of type `TransactionEnvelope`,
the value and operation `focus.op_index`; for `Operation`, the value; for `Memo`, its memo type. Other variants imply
no keys. `verify` fails a variant whose `derived.l1` lacks a key the focus implies, carries one it does not, or holds
another value, and prints the expected object; `xdrcheck-corpus gen` writes it for the entries it generates. Excerpt of
`cap-0038/pool-issuers-order-by-bytes-not-strkey`, whose focus is a pool-share ChangeTrust:

```json
"l1": {"memo_type": "none", "operation_type": "change_trust", "pool_id": "c2a730127d006897b021d6fcb279da68b4f65f9b6a408c74eb2cdd85ea862d5e"}
```
