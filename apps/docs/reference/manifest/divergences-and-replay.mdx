## 7. Known divergences

`conformance.known_divergences[]` records that a specific reader gets this entry wrong in a version range. Fields:
`target`, `versions`, `outcome` and `reference` are required; `level`, `qualifier`, `profile`, `detail`, `fixed_in`,
`status`, `observed`, `evidence`, `finding` and `match` are optional.

- `target`: package or repository (`@stellar/stellar-sdk`, `github.com/stellar/go-stellar-sdk`,
  `stellar/wallet-backend`).
- `versions`: a semver range for packages; for repositories without tags a commit range `A..B` (every commit from A
  to B inclusive on the default branch's first-parent history) or `..B` (everything up to and including B), each
  side 7 to 40 lower-case hex digits. A semver range is alternatives joined by `||`, each `*`, a hyphen range
  `A - B` (inclusive), or space-separated comparators (`=`, `<`, `<=`, `>`, `>=`, or a bare version meaning `=`); a
  version is `MAJOR[.MINOR[.PATCH]]` with an optional leading `v`, `-prerelease` and `+build`. Nothing else (`^`,
  `~`, `x` wildcards) is accepted: `verify --checks schema` fails a range that does not parse, because a consumer
  would otherwise match nothing and drop the divergence silently.
- `level`: `L0`–`L4` ([§10](/reference/manifest/kinds-and-levels#10-conformance-levels-by-kind)) or `replay` (the replay harness).
- `outcome`: `reject` (a **valid** input was rejected), `accepts_invalid` (an invalid input was accepted), `crash`,
  `wrong_value`, `dropped`, `halt`, `hang`.
- `qualifier` (for `level: replay`): the exact result qualifier the harness must report inside the range. The harness
  reports each entry as pass, mishandled or dropped; mishandled carries `wrong_value`, `crash`, `hang` or `halt`;
  dropped carries `silent` (the ledger or transaction is absent with no error), `partial` (some expected facts are
  missing) or `refused` (a declared, verified refusal).
- `profile`: set when the divergence exists only under a non-default decode profile or sandbox (for example Rust
  `Limits::none()`).
- `detail`: what was seen. `reference`: a URL (issue, pull request, advisory). `fixed_in`: version or commit.
- `status`: `fixed`, `fixed_unreleased` (merged upstream, no release yet), `open`, `wont_fix`, `unreported`.
- `observed`: `executed` (run at a version inside the range), `source-reading`, `reported` (reported upstream and not
  re-run). A range that was only partly executed is split into two divergences — the executed part and the rest — so
  `observed: executed` never covers a version nobody ran. `cap-0038/pool-issuers-order-by-bytes-not-strkey` splits
  the Go SDK this way: `>=0.7.0 <0.7.2` executed at v0.7.1, and `<0.6.1` taken from release notes as `reported`.
- `evidence`: path or URL of the transcript or note that shows the divergence.
- `match`: details the observed conformance cell must also show for the divergence to count as observed, beyond the
  outcome class — `{reason?, envelopes_parsed?, rejected_tx_index?}`, at least one. `reason` is the driver's reason
  code (one of the driver protocol's `runResponse.reason.code` values); `envelopes_parsed` is how many envelopes the
  SDK parsed and `rejected_tx_index` an envelope (apply order) that must be among those it rejected, both for a
  divergence at level `L1` of a `ledger` entry and within the ledger's transactions; `rejected_tx_index` needs
  `outcome: reject`. `verify --checks schema` checks all of this. For example
  `"match": {"reason": "decode_error", "rejected_tx_index": 2}`.

Excerpt of `cap-0073/sac-trust-creates-trustline`:

```json
{
  "target": "stellar/wallet-backend",
  "versions": "..764a4f5bcbff5abb0949d93da37f769063013ea0",
  "level": "replay",
  "outcome": "dropped",
  "qualifier": "partial",
  "reference": "https://github.com/stellar/wallet-backend/issues/731",
  "fixed_in": "c152783c054c765c8b51fd26ed313fd1ebc1c50c",
  "status": "fixed",
  "observed": "executed"
}
```

Semantics for the conformance runner and the harness: **inside** the range the divergence must be observed with that
outcome (and qualifier, when given); **outside** every range the reader must pass; a divergence that is observed but
not listed fails the run. A divergence that is `source-reading` or `reported` is asserted only after it has been
executed once; until then it is reported as "expected, unconfirmed".

In the public manifest `status: unreported` therefore appears only on divergences that are plainly not security-relevant (a strictness nit, a documentation gap), and each of those carries a `finding` ID so that the findings check can see that a record exists. `verify --checks schema` rejects a public entry whose divergence is `unreported` and has no `finding`.

## 8. The replay block

### 8.1 Fields

- `unit`: `single` (served alone at its real sequence) or `chain` (served as part of its scenario run, from the first
  ledger).
- `chain`: the chain ID when `unit` is `chain`.
- `requires_prior_state` (default `false`): `true` if a reader needs the earlier ledgers of the same chain for the
  entry to be meaningful (for example a balance update on an existing trustline). Such entries are replayed only
  inside their chain. For `cap-0073/sac-trust-creates-trustline` it is `false`: serving that one ledger gave the same
  wallet-backend rows as replaying its chain from ledger 2 (transcripts in `evidence/wallet-backend-731/`).
- `indexer_scope`: `all` (default) or `sdk-only` (entries indexers are not expected to ingest, such as very old
  protocols).

### 8.2 Chain indexes

Chain membership is recorded once, in the chain's index file `corpus/chains/<id>.json` (schema
`corpus/schema/chain-index.schema.json`; for example `corpus/chains/sac-trust/p28-testnet.json`, chain ID
`sac-trust/p28-testnet`): passphrase, protocol, flag profile, the stellar-core build, the settings applied, and every
ledger's sequence, blob hash and header hash. A chain is one run of one scenario on one passphrase at one target
protocol under one flag profile. The harness finds the chain a variant belongs to through its blob hash, so an entry
with variants in several chains needs no list in the manifest. A chain below Protocol 20 applies no Soroban settings:
its `settings.source` starts with `none` and `settings.files` is empty (every other chain lists at least one file).
A chain whose scenario fixes the apply order of a ledger group records, under `orders`, the group's first step ID
with the `${order_nonce}` the generator chose and the transaction-set shape its search used (`default` or `learned`);
`gen --check` repeats the search and reports a different nonce or shape as a difference.

Only the ledgers that hold an entry are vendored as blobs; the replay harness serves the rest of a chain from the
run's record-marked meta stream, which the index names under `stream` (`path`, `sha256`, `records`). Chains written
by `xdrcheck-corpus gen` keep that stream in the repository next to the index, as
`chains/<scenario>/p<NN>-<network>.meta.xdr.zst` (one zstd frame, level 19, with the content checksum); `stream.path`
is relative to the corpus root and `stream.sha256` is the sha256 of the **uncompressed** stream. The two
`sac-trust` chains name their raw stream under `evidence/` instead (relative to the repository root). Raw meta bytes
are not reproducible, so `xdrcheck-corpus gen` rewrites a committed chain's bytes only when a regeneration no longer
passes `gen --check` against it; otherwise it writes the committed stream's bytes again.

The harness may additionally place any entry in a renumbered *stream* for load and memory tests (ledger sequences
rewritten to make unrelated ledgers contiguous). That transformation is a report-time artefact: it is never recorded
in the manifest, the transformed bytes never enter the corpus, and stream results are never used for known-divergence
assertions.

### 8.3 How a ledger blob is served

A `LedgerCloseMeta` blob reaches an indexer through an input it already consumes. The corpus bytes are not changed.

- **SEP-54 object** (data-lake layout): the object value is the XDR of `LedgerCloseMetaBatch\{startSequence = seq,
  endSequence = seq, ledgerCloseMetas = [blob]\}` — 12 bytes (`seq`, `seq`, `1`, each a big-endian uint32) followed by
  the blob, zstd-compressed. For the two `history` entries this is byte-identical to the public lake's decompressed
  object ([§4.5](/reference/manifest/entry-fields#4-5-blobs-and-how-a-blob-relates-to-its-source)). The key follows the SEP-54 layout with one ledger per batch, at the ledger's real sequence for a
  `single` unit. The store root carries `.config.json` with the passphrase, `"version":"1.0"`, `"compression":"zstd"`,
  `"ledgersPerBatch":1` and `"batchesPerPartition":64000`. One store per passphrase.
- **`getLedgers` item** (the RPC method's v30.0.0 field types): `hash` (hex, the header hash stored in the blob, not
  recomputed), `sequence` (number), `ledgerCloseTime` (string, decimal seconds), `headerXdr` (base64 of the
  `LedgerHeaderHistoryEntry` inside the blob), `metadataXdr` (base64 of the blob, verbatim).
- Consumers require strictly consecutive sequences and none checks the previous-ledger hash, so a `single` unit at its
  real sequence is valid input. The passphrase is enforced through transaction hashes, so a run uses one passphrase.
