## Mistake 3: participants from the envelope instead of the meta

### XDR301

**Participants harvested from the authorization tree or invocation arguments.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |
| How to fix | take participants from meta (entry changes, nonce entries, events of a verified contract), not from the authorization tree or call arguments |
| Default severity | error (`severity: {XDR301: …}` changes it) |
| Default rule set | yes |
| Guide | [Participants from meta](/hardening/overview) |
| Self-audit checklist item | HC-301 |
| Demonstrating corpus entry | `cap-0046/auth-unmatched-entries-succeed` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr3xx/xdr301` |

**What it reports**

A value read from an authorization entry or from invocation arguments reaches a participant sink (or a configured
state-change sink) without corroboration from meta. Sources are the credential addresses of
`SorobanAuthorizationEntry`, delegate addresses, `RootInvocation` and `SubInvocations`, the contract address and
create-contract preimages of a `SorobanAuthorizedFunction`, `InvokeContractArgs.ContractAddress` and `Args`, and
create-contract preimages.

The report is silent when the value is used only as a key into, or compared with, a set built from meta, and the
sink depends on that membership test.

**Why it matters**

The host authenticates only the authorization entries a `require_auth` call matched; a successful transaction can
carry any number of others, naming any address. The proof that an address authorised an operation is the nonce
entry the host wrote for it in the meta. A reader that adds every address in the tree lets a submitter write into
anyone's history.

**Example**

Reported:

```go
// lint/testdata/xdr3xx/xdr301/bad.go
// (a) A credential address goes straight into the participant set.
func credentialParticipants(tx ingest.LedgerTransaction, entries []xdr.SorobanAuthorizationEntry) addrSet {
	participants := addrSet{}
	_ = tx.GetFeeChanges()
	for _, e := range entries {
		if e.Credentials.Type != xdr.SorobanCredentialsTypeSorobanCredentialsAddress {
			continue
		}
		addr, err := e.Credentials.MustAddress().Address.String()
		if err != nil {
			continue
		}
		participants.Add(addr)
	}
	return participants
}
```

Not reported: authorizers come from the nonce entries in meta.

```go
// lint/testdata/xdr3xx/xdr301/good.go
// (a) Authorizers are the owners of the nonce entries the host created.
func authorizers(tx ingest.LedgerTransaction, opIndex uint32) (addrSet, error) {
	participants := addrSet{}
	changes, err := tx.GetOperationChanges(opIndex)
	if err != nil {
		return nil, err
	}
	for _, c := range changes {
		if c.Type != xdr.LedgerEntryTypeContractData || c.Post == nil {
			continue
		}
		cd := c.Post.Data.MustContractData()
		if cd.Key.Type != xdr.ScValTypeScvLedgerKeyNonce {
			continue
		}
		a, err := cd.Contract.String()
		if err != nil {
			return nil, err
		}
		participants.Add(a)
	}
	return participants, nil
}
```

**Limits**

An indexer that deliberately keeps "declared, unverified" relations apart from participants should suppress the
report with that reason. The host also requires authorization for some top-level host functions (a deploy from an
address). When the operation's own host function and the authorization tree reach the same sink through a function
value (a callback both paths call), the rule's source is type-based and cannot tell them apart: that report is a
known false positive of the rule, and it is suppressed with a reason that says the path is the operation's own host
function of a successful transaction.

**Configure and suppress**

Turn the rule off by leaving XDR301 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR301 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR302

**Envelope operation fields used as participants without a success gate.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |
| How to fix | add operation accounts only after a success check (LedgerTransaction.Successful()), or take them from meta |
| Default severity | error (`severity: {XDR302: …}` changes it) |
| Default rule set | yes |
| Guide | [Participants from meta](/hardening/overview) |
| Self-audit checklist item | HC-302 |
| Demonstrating corpus entry | `cap-0015/fee-bump-inner-failed` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr3xx/xdr302` |

**What it reports**

An operation source or an account named in an operation body (payment and path-payment destinations,
`CreateAccountOp.Destination`, claimants, trustors, the clawback source, the sponsored account, revoked
sponsorship owners) reaches a participant sink at a point not dominated by a success check
(`LedgerTransaction.Successful()`, `TransactionResult(Pair).Successful()`, or a variable holding one). A helper
that returns such accounts without checking success is silent; its unguarded call sites are reported.

**Why it matters**

A failed transaction still lands in the ledger and its fee is charged, so the transaction source and the fee
source are always participants. Operation accounts are participants only when the operation was applied: a
failed payment never touched its destination. Adding them anyway lets anyone place entries in another account's
history for the price of a fee.

**Example**

Reported:

```go
// lint/testdata/xdr3xx/xdr302/bad.go
// (c) The success check exists but comes after the envelope accounts were
// taken (the shape fixed upstream by moving the check up).
func opParticipants(tx ingest.LedgerTransaction, op xdr.Operation) []string {
	_ = tx.FeeChanges
	participants := []string{}
	for _, a := range destinations(op) {
		participants = append(participants, a.Address())
	}
	if !tx.Successful() {
		return participants
	}
	return participants
}
```

Not reported:

```go
// lint/testdata/xdr3xx/xdr302/good.go
// (a) The same as bad (c) with the check first: a failed transaction is
// attributed to its source and fee-bump source only.
func opParticipantsGated(tx ingest.LedgerTransaction, op xdr.Operation) []string {
	_ = tx.FeeChanges
	if !tx.Successful() {
		sourceOnly := []string{tx.Envelope.SourceAccount().ToAccountId().Address()}
		if tx.Envelope.IsFeeBump() {
			sourceOnly = append(sourceOnly, tx.Envelope.FeeBumpAccount().ToAccountId().Address())
		}
		return sourceOnly
	}
	participants := []string{}
	for _, a := range destinations(op) {
		participants = append(participants, a.Address())
	}
	return participants
}
```

**Limits**

A success check in a caller in another package is not seen.

**Configure and suppress**

Turn the rule off by leaving XDR302 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR302 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR303

**Participant builder that never reads meta.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |
| How to fix | derive participants from the transaction meta (changes and events), not from the envelope alone |
| Default severity | warning (`severity: {XDR303: …}` changes it) |
| Default rule set | yes |
| Guide | [Participants from meta](/hardening/overview) |
| Self-audit checklist item | HC-303 |
| Demonstrating corpus entry | `cap-0073/sac-trust-creates-trustline` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr3xx/xdr303` |

**What it reports**

A function that writes a participant sink where neither it, its same-package callees, nor a same-package caller
reads any meta: fee changes, operation changes, `UnsafeMeta`, `GetChanges` and its variants, contract events,
`xdr.TransactionMeta…`, `xdr.LedgerEntryChange…` or `ingest.Change`.

**Why it matters**

Some participants exist only in the meta: the holder of a trustline the Stellar Asset Contract created, an
account a contract paid, an authorizer recorded by its nonce entry. A participant builder that reads only the
envelope misses all of them. It is a coarse backstop with little noise, since a real indexer reads at least the
fee changes.

**Example**

Reported:

```go
// lint/testdata/xdr3xx/xdr303/bad.go
// (a) A builder that reads only the envelope's operations.
func EnvelopeParticipants(tx ingest.LedgerTransaction) []string {
	var participants []string
	participants = append(participants, tx.Envelope.SourceAccount().ToAccountId().Address())
	for _, op := range tx.Envelope.Operations() {
		if op.SourceAccount != nil {
			participants = append(participants, op.SourceAccount.ToAccountId().Address())
		}
	}
	return participants
}
```

Not reported:

```go
// lint/testdata/xdr3xx/xdr303/good.go
// (a) A builder that also reads fee changes.
func FeeAwareParticipants(tx ingest.LedgerTransaction) []string {
	var participants []string
	participants = append(participants, tx.Envelope.SourceAccount().ToAccountId().Address())
	for _, c := range tx.FeeChanges {
		if c.Type == xdr.LedgerEntryChangeTypeLedgerEntryUpdated && c.Updated.Data.Type == xdr.LedgerEntryTypeAccount {
			participants = append(participants, c.Updated.Data.Account.AccountId.Address())
		}
	}
	return participants
}
```

**Configure and suppress**

Turn the rule off by leaving XDR303 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR303 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR304

**Token-shaped contract event trusted without checking the emitting contract.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |
| How to fix | compare the event's ContractId with asset.ContractID(passphrase) before trusting its asset or accounts |
| Default severity | error (`severity: {XDR304: …}` changes it) |
| Default rule set | yes |
| Guide | [Deriving participants](/hardening/overview) |
| Self-audit checklist item | HC-305 |
| Demonstrating corpus entry | `cap-0067/forged-token-event-from-unrelated-contract` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr3xx/xdr304` |

**What it reports**

A value read from the topics or data of a contract event reaches a participant sink, or is parsed into an asset
(an `xdr.Asset`, a catalogued asset constructor, a split on `":"`, a configured `sinksmovement` call), at a point
not dominated by a comparison of the event's `ContractId` with an expected contract ID.

The report is silent after `ev.ContractId` is compared with a contract ID derived from the asset and the network
passphrase (`asset.ContractID(passphrase)`, the shape go-stellar-sdk's token transfer processor uses), after a
configured verifier (`sanitizersevent`), and for a sink keyed by the event's contract ID: a configured movement
sink that takes it as an argument, or a configured sink (`sinksparticipant`, `sinksmovement`) called on a builder
that was given it earlier in the chain, such as `b.WithToken(contractID).WithAccount(to)`, directly or through a
variable or a helper that renders the ID. A record kept explicitly "for contract C" is not a claim
about another contract's asset.

**Why it matters**

The host fills an event's contract ID from the executing contract; the topics and data are whatever that contract
passes (soroban-env-host v30.0.0, `src/host.rs` and `src/events/mod.rs`). Anyone can deploy a contract that emits
a four-topic `transfer` naming a victim account and a real classic asset. A reader that credits the asset or adds
the named account as a participant lets a stranger write into another user's history.

**Example**

Reported:

```go
// lint/testdata/xdr3xx/xdr304/bad.go
// (a) The recipient topic of a transfer-shaped event becomes a participant.
func transferParticipants(tx ingest.LedgerTransaction, participants map[string]bool) error {
	events, err := tx.GetContractEvents()
	if err != nil {
		return err
	}
	for _, ev := range events {
		topics := ev.Body.V0.Topics
		if len(topics) < 3 {
			continue
		}
		to, ok := topics[2].GetAddress()
		if !ok {
			continue
		}
		s, _ := to.String()
		participants[s] = true
	}
	return nil
}
```

Not reported:

```go
// lint/testdata/xdr3xx/xdr304/good.go
// (a) The recipient is taken only from the asset's own contract, the shape
// of the SDK's token transfer processor.
func sacTransferParticipants(tx ingest.LedgerTransaction, asset xdr.Asset, passphrase string, participants map[string]bool) error {
	expected, err := asset.ContractID(passphrase)
	if err != nil {
		return err
	}
	events, err := tx.GetContractEvents()
	if err != nil {
		return err
	}
	for _, ev := range events {
		if ev.ContractId == nil || *ev.ContractId != xdr.ContractId(expected) {
			continue
		}
		topics := ev.Body.V0.Topics
		if len(topics) < 3 {
			continue
		}
		to, ok := topics[2].GetAddress()
		if !ok {
			continue
		}
		s, _ := to.String()
		participants[s] = true
	}
	return nil
}
```

**Limits**

Any argument earlier in the builder chain that carries the emitting contract's ID keys the builder; the rule does
not check which setter took it. Writing the account into a plain participant set beside a keyed builder is still
reported. Verification done in another package is not seen.

A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).
