## Mistake 2: no depth or size cap on recursive structures

### XDR201

**Recursion over a self-referential xdr type with no depth bound.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | pass a depth counter down the recursion and stop at a limit at or above what stellar-core admits |
| Default severity | warning (`severity: {XDR201: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-201 |
| Fixtures | `lint/testdata/xdr2xx/xdr201` |

**What it reports**

A function or closure that recurses, directly or through other functions of the same package, passing a value of a
self-referential xdr type (after dereference, slice element or range element), with no depth bound. The
self-referential types are computed from the loaded `xdr` package: `SorobanAuthorizedInvocation`,
`SorobanDelegateSignature`, the `ScVal` group, `ClaimPredicate` and the `ScSpecTypeDef` group at go-stellar-sdk
v0.9.0. The report is an error when a level merges its children's results (`Union`, `append(x, ys...)`), and a
warning otherwise.

A bound is an integer parameter, receiver field or captured variable that every recursive call changes by a
constant and that is compared with a limit before recursing, leading to a return or break; or a configured budget
method (`budgetmethods`) called and error-checked first.

**Why it matters**

The host checks only the authorization entries that a `require_auth` call matched. Unmatched entries, nested trees included, are never examined, and a transaction carrying them succeeds, so the shape of the tree is the submitter's choice.

A bound silences this rule only. A constant bound on a path fed from ledger meta is then examined by XDR207, which
reports it when it is below what stellar-core admits, and the behaviour past the bound by XDR206. A low fixed cap
is never the quiet option.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr201/bad.go
// (a) A named function over SubInvocations.
func countContracts(inv xdr.SorobanAuthorizedInvocation) int {
	n := 0
	if inv.Function.Type == xdr.SorobanAuthorizedFunctionTypeSorobanAuthorizedFunctionTypeContractFn {
		n++
	}
	for _, sub := range inv.SubInvocations {
		n += countContracts(sub)
	}
	return n
}
```

Not reported: the depth limit comes from configuration.

```go
// lint/testdata/xdr2xx/xdr201/good.go
// (a) A depth parameter compared with a bound from configuration.
func walkBounded(cfg config, inv xdr.SorobanAuthorizedInvocation, depth int) error {
	if depth > cfg.MaxAuthDepth {
		return errTooDeep
	}
	for _, sub := range inv.SubInvocations {
		if err := walkBounded(cfg, sub, depth+1); err != nil {
			return err
		}
	}
	return nil
}
```

**Limits**

"The walk only runs for successful transactions" is deliberately not a bound. Recursion through interface
dispatch, through `fmt` and `Stringer` (`ScVal.String`), or across packages is not seen. Walkers over structures
that stellar-core bounds itself (`ClaimPredicate`, at most 4 levels) are reported and can be suppressed with that
reason.

**Configure and suppress**

Turn the rule off by leaving XDR201 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR201 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR202

**Iterative walker with an unbounded worklist.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | count nodes (or the worklist length) inside the loop and stop at a limit at or above what stellar-core admits |
| Default severity | warning (`severity: {XDR202: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-202 |
| Fixtures | `lint/testdata/xdr2xx/xdr202` |

**What it reports**

A loop that pops values of a self-referential xdr type from a slice and appends their children, with no comparison
of the worklist length or of a counter incremented in the loop against a bound.

**Why it matters**

Rewriting a recursive walk as a loop with an explicit stack removes the recursion but not the problem: the work
still grows with a tree the submitter shaped (see XDR201). The bound has to be there in either form.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr202/bad.go
// The natural rewrite that silences XDR201 and moves the problem.
func contractsIterative(root xdr.SorobanAuthorizedInvocation) []string {
	var out []string
	stack := []xdr.SorobanAuthorizedInvocation{root}
	for len(stack) > 0 {
		inv := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		if fn, ok := inv.Function.GetContractFn(); ok {
			s, _ := fn.ContractAddress.String()
			out = append(out, s)
		}
		stack = append(stack, inv.SubInvocations...)
	}
	return out
}
```

Not reported:

```go
// lint/testdata/xdr2xx/xdr202/good.go
// An explicit stack with a node counter and a length check.
func contractsBounded(root xdr.SorobanAuthorizedInvocation, maxNodes int) ([]string, error) {
	var out []string
	stack := []xdr.SorobanAuthorizedInvocation{root}
	visited := 0
	for len(stack) > 0 {
		visited++
		if visited > maxNodes || len(stack) > maxNodes {
			return nil, errTooMany
		}
		inv := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		if fn, ok := inv.Function.GetContractFn(); ok {
			s, _ := fn.ContractAddress.String()
			out = append(out, s)
		}
		stack = append(stack, inv.SubInvocations...)
	}
	return out, nil
}
```

**Configure and suppress**

Turn the rule off by leaving XDR202 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR202 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR203

**Decoded integer used as an allocation size or loop bound.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | compare the decoded integer with an upper bound before allocating or looping on it |
| Default severity | warning (`severity: {XDR203: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-203 |
| Demonstrating corpus entry | `xdr-strict/length-prefix-exceeds-input` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr2xx/xdr203` |

**What it reports**

An integer read from a decoded xdr value used as an allocation size (`make`, `strings.Repeat`, `bytes.Repeat`) or a
loop bound with no dominating upper-bound comparison. `len` of a decoded slice is not reported: the decoder
already materialised it, and go-xdr caps its own pre-allocation and checks lengths against the remaining input.

**Why it matters**

A `u32` in a contract value or an operation is any number the submitter chose. Using it as a size lets one
transaction make the reader allocate gigabytes or spin for billions of iterations.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr203/bad.go
func bytesFor(v xdr.ScVal) []byte {
	if v.U32 == nil {
		return nil
	}
	return make([]byte, *v.U32)
}
```

Not reported:

```go
// lint/testdata/xdr2xx/xdr203/good.go
func bytesBounded(v xdr.ScVal) []byte {
	if v.U32 == nil {
		return nil
	}
	n := *v.U32
	if n > maxAlloc {
		return nil
	}
	return make([]byte, n)
}
```

**Limits**

The value is followed through assignments, conversions and arithmetic, not through other calls.

**Configure and suppress**

Turn the rule off by leaving XDR203 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR203 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR204

**Persisted serialisation of a recursive value with no length check.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | check the serialised length before writing it to the database |
| Default severity | info (`severity: {XDR204: …}` changes it) |
| Default rule set | no: opt-in, add XDR204 to `rules` |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-209 |
| Demonstrating corpus entry | `cap-0046/overly-large-values-golden` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr2xx/xdr204` |

**What it reports**

A serialisation of a value of a self-referential xdr type (`MarshalBinary`, `MarshalBase64`, `xdr.MarshalBase64`,
`xdr.MarshalHex`, `fmt.Sprint…`) passed to the database with no check of its length.

**Why it matters**

Contract values in events and contract data can be large and deeply nested within the network's limits. Persisting
their serialised form without a size check moves an unbounded value into a column, an index or a message that may
have a limit of its own.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr204/xdr204.go
func storeValue(db *sql.DB, v xdr.ScVal) error {
	s, err := xdr.MarshalBase64(v)
	if err != nil {
		return err
	}
	_, err = db.Exec("INSERT INTO vals (v) VALUES ($1)", s)
	return err
}
```

Not reported:

```go
// lint/testdata/xdr2xx/xdr204/xdr204.go
func storeChecked(db *sql.DB, v xdr.ScVal) error {
	s, err := xdr.MarshalBase64(v)
	if err != nil {
		return err
	}
	if len(s) > maxStored {
		return nil
	}
	_, err = db.Exec("INSERT INTO vals (v) VALUES ($1)", s)
	return err
}
```

**Limits**

Opt-in and informational: storing the raw value is often exactly what a reader should do (the guide recommends
keeping the raw XDR beside derived values); the rule only asks that the size be considered.

**Configure and suppress**

Turn the rule off by leaving XDR204 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR204 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR205

**Decoder with limits disabled.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | decode with limits: keep the default MaxDepth and set MaxInputLen, or use xdr.SafeUnmarshal |
| Default severity | error (`severity: {XDR205: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-204 |
| Demonstrating corpus entry | a `limits/` entry at the Soroban host's value depth limit |
| Fixtures | `lint/testdata/xdr2xx/xdr205` |

**What it reports**

- An error for any use of go-xdr's `DecodeUnlimitedDepth`, or a `DecodeOptions` literal whose `MaxDepth` is an
  unlimited sentinel.
- A warning for `xdr.Unmarshal` or `xdr.UnmarshalWithOptions` on a reader without a `Len() int` method (a network
  body, a decompression stream) when `MaxInputLen` is not set.


**Why it matters**

The decoder's limits are what bound everything a reader does afterwards. With the depth limit disabled, one deeply nested value exhausts the stack; with no input length, a length prefix can claim more data than the stream holds.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr205/bad.go
// Depth unlimited, from a network body.
func decodeUnlimited(body io.Reader) (xdr.ScVal, error) {
	var v xdr.ScVal
	_, err := xdr.UnmarshalWithOptions(body, &v, xdr.DecodeOptions{MaxDepth: xdr3.DecodeUnlimitedDepth})
	return v, err
}
```

Not reported:

```go
// lint/testdata/xdr2xx/xdr205/good.go
// A stream with MaxInputLen set.
func decodeLimited(r io.Reader, n int) (xdr.ScVal, error) {
	var v xdr.ScVal
	_, err := xdr.UnmarshalWithOptions(r, &v, xdr.DecodeOptions{MaxInputLen: n})
	return v, err
}
```

**Limits**

Options held in a variable instead of a literal are not examined.

**Configure and suppress**

Turn the rule off by leaving XDR205 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR205 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR206

**Behaviour at a bound differs from the declared overflow policy.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | make the branch past the bound do what overflowpolicy declares (fail the ledger, or skip and set the flag); never exit the process |
| Default severity | warning (`severity: {XDR206: …}` changes it) |
| Default rule set | yes |
| Guide | [What to do at a bound: a trade-off](/hardening/overview) |
| Self-audit checklist item | HC-205 |
| Fixtures | `lint/testdata/xdr2xx/xdr206` |

**What it reports**

For a walk that has a bound (XDR201 or XDR202 accepted it), the branch taken past the bound does something other
than what the project declared in `overflowpolicy`:

- under any policy, it ends the process: `panic`, `log.Fatal…`, `os.Exit` or a configured `haltingfuncs` entry;
- under `halt-ledger`, it returns without an error (`return nil`, `continue`, `break`), silently truncating;
- under `skip-and-flag`, it returns or continues without setting one of the configured `overflowflags`.

With no policy declared only the first case is reported, and the message asks for a declaration.

**Why it matters**

Past a bound a reader of ledger meta has two defensible choices, and both cost something. Stopping the ledger
with a typed, alertable error stores nothing wrong but leaves ingestion stopped on a ledger stellar-core accepted
until the bound is raised. Skipping the field, flagging the record as incomplete and keeping the raw XDR keeps
ingestion up but leaves the record incomplete until it is re-derived. A crash is neither, and a silent truncation
is the partial drop no reader wants. The linter checks that the code does what was declared; it does not choose.

**Example**

Reported under any policy:

```go
// lint/testdata/xdr2xx/xdr206/xdr206.go
func walkPanics(l limits, inv xdr.SorobanAuthorizedInvocation, depth int) {
	if depth > l.MaxAuthDepth {
		panic("auth tree too deep")
	}
	for _, sub := range inv.SubInvocations {
		walkPanics(l, sub, depth+1)
	}
}
```

Compliant under `halt-ledger`:

```go
// lint/testdata/xdr2xx/xdr206/xdr206.go
// Without a declared policy, stopping with an error and skipping are both
// left alone.
func walkError(l limits, inv xdr.SorobanAuthorizedInvocation, depth int) error {
	if depth > l.MaxAuthDepth {
		return errTooDeep
	}
	for _, sub := range inv.SubInvocations {
		if err := walkError(l, sub, depth+1); err != nil {
			return err
		}
	}
	return nil
}
```

**Limits**

Whether an error returned under `halt-ledger` really stops the ledger, or a caller swallows it, is not decided
locally.

**Configure and suppress**

Turn the rule off by leaving XDR206 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR206 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR207

**Bound below what stellar-core admits, on a path fed from ledger meta.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | raise the constant to at least what stellar-core admits for that structure, or read the bound from configuration |
| Default severity | warning (`severity: {XDR207: …}` changes it) |
| Default rule set | yes |
| Guide | [What stellar-core admits](/hardening/overview) |
| Self-audit checklist item | HC-206 |
| Demonstrating corpus entry | a contract event whose data is nested as deep as the Soroban host converts |
| Fixtures | `lint/testdata/xdr2xx/xdr207` |

**What it reports**

A depth bound that is a compile-time constant, in a walk fed from ledger meta, below what stellar-core admits
for that structure; or, for a structure with no established limit, any such constant (as info). A bound read from
configuration is not examined: the project owns that number.

Floors shipped with the linter (`floors` in the configuration overrides or extends them):

| Structure | Floor | Source |
|---|---|---|
| `ClaimPredicate` | 4 levels | stellar-core v30.0.0, `src/transactions/CreateClaimableBalanceOpFrame.cpp` |
| `SorobanAuthorizedInvocation`, `SorobanDelegateSignature`, `ScSpecTypeDef` | not established | |

**Why it matters**

"Add a cap" is the first fix a team reaches for, and a cap below what stellar-core admits makes a reader of
consensus meta reject or mangle a valid ledger. A low fixed cap trades an XDR201 report for this one; it is never
the quiet option. Readers of untrusted input before submission (for example `net/http` handlers) are not
reported: a tighter cap there is legitimate.

**Example**


```go
// lint/testdata/xdr2xx/xdr207/bad.go
func walkEventValue(v xdr.ScVal, depth int) error {
	if depth > maxScValDepth {
		return errTooDeep
	}
	if vec, ok := v.GetVec(); ok && vec != nil {
		for _, x := range *vec {
			if err := walkEventValue(x, depth+1); err != nil {
				return err
			}
		}
	}
	return nil
}
```


```go
// lint/testdata/xdr2xx/xdr207/good.go
func walkAtFloor(v xdr.ScVal, depth int) error {
	if depth > maxValueDepth {
		return errTooDeep
	}
	if vec, ok := v.GetVec(); ok && vec != nil {
		for _, x := range *vec {
			if err := walkAtFloor(x, depth+1); err != nil {
				return err
			}
		}
	}
	return nil
}
```

**Limits**

Bounds computed at run time are not examined. A function that serves both meta and pre-submission input is
treated as a meta reader.

Turn the rule off by leaving XDR207 out of `rules` in `.xdrlint.yml` or a profile. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).
