## Suppression hygiene

### XDR000

**Suppression without a reason, naming an unknown rule, or suppressing nothing.**


| | |
|---|---|
| Family | XDR0xx: suppression hygiene |
| How to fix | give the directive or entry a reason after the rule ID, name a rule that exists, or delete the suppression that matches nothing |
| Default severity | error (`severity: {XDR000: …}` changes it) |
| Default rule set | yes |
| Documentation | [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing) |
| Fixtures | `lint/testdata/xdr0xx/xdr000` |

**What it reports**

A suppression that cannot be trusted:

- an inline directive (`//xdrlint:ignore`) with no reason, naming an unknown rule, malformed, or naming XDR000;
- an entry of an external suppression file with no reason, an unknown rule, none of a function, an anchor and a
  line, or an unknown key;
- any suppression, inline or external, that suppresses nothing.

**Why it matters**

A suppression is a reviewed statement that a report is understood. One without a reason cannot be reviewed, and
one that suppresses nothing has outlived the code it was written for. Reporting stale suppressions is what makes a
frozen suppression list able to fail: when the site changes or the rule stops firing, the run turns red.

**Example**

Reported:

```go
// lint/testdata/xdr0xx/xdr000/bad.go
func describe(tx xdr.TransactionEnvelope) []string {
	var names []string

	//xdrlint:ignore XDR201
	names = append(names, tx.SourceAccount().ToAccountId().Address())

	//xdrlint:ignore XDR999 not a rule of this linter
	names = append(names, tx.Memo().Type.String())

	// xdrlint:ignore XDR102 a space after the slashes would hide the directive

	//xdrlint:allow XDR102 wrong verb

	//xdrlint:ignore XDR000 hygiene is not optional

	//xdrlint:ignore XDR10 a typo

	return names
}
```

Not reported: a well-formed directive that marks a sink.

```go
// lint/testdata/xdr0xx/xdr000/good.go
// storeKey is an account-key sink; the directive is well formed and the key
// is reduced to the base account first.
//
//xdrlint:sink accountkey
func storeKey(keys map[string]bool, a xdr.MuxedAccount) {
	acc := a.ToAccountId()
	keys[acc.Address()] = true
}
```

**Limits**

XDR000 cannot itself be suppressed.

**Configure and suppress**

Turn the rule off by leaving XDR000 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR000 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


## Mistake 1: trusting fields stellar-core does not validate

### XDR101

**Address built from a memo.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | route only a u64 to_muxed_id (or a MEMO_ID) into a muxed address; keep memo text and hash as data, never as an ID |
| Default severity | error (`severity: {XDR101: …}` changes it) |
| Default rule set | yes |
| Guide | [The event routing ID](/hardening/overview) |
| Self-audit checklist item | HC-101 |
| Demonstrating corpus entry | `cap-0067/to-muxed-id-text-from-memo` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr101` |

**What it reports**

A value derived from a transaction memo reaches the construction of a muxed address: an
`xdr.MuxedAccountMed25519`, `xdr.MuxedEd25519Account` or `xdr.MuxedContract` literal, `strkey.MuxedAccount.SetID`,
`strkey.MuxedContract.SetID`, `strkey.Encode` with a muxed version byte, `xdr.NewMuxedAccount` or
`xdr.MuxedAccountFromAccountId`.

Sources are the memo accessors (`xdr.Memo.Id`, `Text`, `Hash`, `RetHash` and their `Get…`/`Must…` forms,
`TransactionEnvelope.Memo()`, `ingest.LedgerTransaction.Memo()`), the token transfer processor's `MuxedInfo`
getters, and any value assigned on a path where a type switch chose the text or hash arm of a `MuxedInfo`.

**Why it matters**

stellar-core never checks what a memo contains, and since CAP-67 it copies the memo of a classic payment into
the event's `to_muxed_id`, which can therefore be a 64-bit ID, a text string or 32 bytes. A text or hash memo is
not a routing ID, and an address built from one names an account that nobody controls. Store a memo-derived ID
as an ID, next to the base account, and never turn it into an `M…` address.

**Example**

Reported:

```go
// lint/testdata/xdr1xx/xdr101/bad.go
// (b) A type switch whose text and hash arm sets id = 0 and falls through
// to SetID.
func destinationFromSwitch(to string, info *token_transfer.MuxedInfo) (string, error) {
	var id uint64
	switch c := info.Content.(type) {
	case *token_transfer.MuxedInfo_Id:
		id = c.Id
	case *token_transfer.MuxedInfo_Text, *token_transfer.MuxedInfo_Hash:
		id = 0
	default:
		return "", nil
	}
	var m strkey.MuxedContract
	if err := m.SetContractID(to); err != nil {
		return "", err
	}
	m.SetID(id)
	return m.Address()
}
```

Not reported: the ID is stored as an ID.

```go
// lint/testdata/xdr1xx/xdr101/good.go
// (a) The memo-derived routing ID stored only as an ID, never as an address.
func setToMuxedID(t *transfer, info *token_transfer.MuxedInfo) {
	if info == nil {
		return
	}
	switch c := info.Content.(type) {
	case *token_transfer.MuxedInfo_Id:
		id := c.Id
		t.ToMuxedID = &id
	case *token_transfer.MuxedInfo_Text, *token_transfer.MuxedInfo_Hash:
		// A memo, not a routing ID: not stored as one.
	}
}
```

**Limits**

A memo copied into a struct field and encoded into an address in another package is not followed. An indexer
that deliberately renders memo-routed addresses for display should suppress the report with that reason.

**Configure and suppress**

Turn the rule off by leaving XDR101 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR101 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR102

**Unnormalised address used as an identity key.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | key on the base account: MuxedAccount.ToAccountId(), or a switch on ScAddress.Type that handles the muxed, claimable-balance and pool kinds |
| Default severity | error (`severity: {XDR102: …}` changes it) |
| Default rule set | yes |
| Guide | [Muxed and signed-payload handling](/hardening/overview) |
| Self-audit checklist item | HC-102 |
| Demonstrating corpus entry | `cap-0027/muxed-source-and-destination-max-ids` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr102` |

**What it reports**

An address string taken from a value that can be muxed, a signed payload, or a non-account kind is used as a
participant or account key without being reduced to its base account or having its kind checked.

Sources are `(*xdr.MuxedAccount).Address()` and `GetAddress()` (also through `TransactionEnvelope.SourceAccount()`,
`FeeBumpAccount()`, `Operation.SourceAccount` and operation destinations), `ingest.LedgerTransaction.AccountMuxed()`
and `FeeAccountAddress()`, `xdr.ScAddress.String()`, `(*xdr.SignerKey).Address()` and the keys of
`AccountEntry.SignerSummary()`. Sinks are participant sets and configured account-key types and functions
(`sinksparticipant`, `sinksaccountkey`).

An address can be wrong in two ways, and each is checked on its own: it can be in muxed form (`M…`, `W…`), or it
can be of a kind that is not an account (`B…` claimable balance, `L…` liquidity pool, `P…`, `T…`, `X…` signers).

The report is silent when the value went through `MuxedAccount.ToAccountId()`, when a dominating switch or `if` on
`ScAddress.Type` handles the muxed kinds and excludes or routes the claimable-balance and liquidity-pool kinds,
when a configured normaliser (`sanitizersaddress`) produced it, or when the address is the contract of a contract
data entry the host wrote into meta (never a muxed kind). Besides:

- **A sink that normalises.** An account-key type whose own `Value()` decodes the strkey, reduces the muxed
  account kind and refuses any payload that is not a 32-byte key (as `AddressBytea.Value()` does) stores a muxed
  address as its base key; so does a function whose string parameter only becomes such a type (a builder's
  `WithAccount`). Only the non-account kinds are reported there, because that type refuses them with a write
  error. The property is read from the `Value()` body, in whichever package declares it.
- **A re-parse of the same entry.** A sink on the passing branch of `sac.ContractBalanceFromContractData(entry, …)`
  (ok only when the balance key's holder is a contract) is kind-checked, when the address was read from the same
  ledger entry.
- **Contract storage.** The host refuses to store a claimable-balance, liquidity-pool or muxed address, so an
  address read from the key or value of a contract-data entry is a `G…` or `C…` address. This is decided per call
  of a shared helper: `addrString(entry.Key)` is exempt, `addrString(topics[1])` is not.
- **Where `B…` and `L…` come from.** A contract can never store, return or emit a claimable-balance or pool
  address: the host refuses to convert one to a contract value. Such an address reaches a reader only in events the
  host emits for the Stellar Asset Contract, or in the envelope (invocation arguments, the authorization tree), which
  is submitter bytes. The non-account kind is reported only for an address that may have been read from a contract
  event's topics or data or from those envelope fields, and not for one decoded on the branch where the event's name
  is one the Stellar Asset Contract never emits (`case "supply": decode(topics)`).

**Why it matters**

stellar-core uses only the ed25519 key of a muxed account; the 64-bit ID is never validated. Storing the `M…`
form as identity splits one account into as many accounts as there are IDs, and fixed-width columns truncate
`M…`, `P…` and `B…` strkeys. `ScAddress.String()` renders every kind SEP-23 defines, including claimable
balances (`B…`) and liquidity pools (`L…`), which are not accounts at all.

**Example**

Reported: the operation source is used as identity in its muxed form.

```go
// lint/testdata/xdr1xx/xdr102/bad.go
// (a) The operation source rendered with Address(): M… when muxed.
func operationParticipants(op xdr.Operation, participants set) {
	participants.Add(op.SourceAccount.Address())
}
```

Not reported:

```go
// lint/testdata/xdr1xx/xdr102/good.go
// (a) Reduced to the base account first.
func operationParticipantsBase(op xdr.Operation, tx *ingest.LedgerTransaction, participants set) {
	if op.SourceAccount != nil {
		participants.Add(op.SourceAccount.ToAccountId().Address())
	}
	participants.Add(tx.Envelope.SourceAccount().ToAccountId().Address())
	if acc, err := tx.Account(); err == nil {
		participants.Add(acc)
	}
}
```

**Limits**

Flows through `map[string]interface{}` are not followed. Sinks in another module are seen only when configured.
Values decoded from bytes (an RPC response, base64 topics) are not recognised as events or envelope fields, so an
address read from them loses the non-account-kind aspect (a false negative). The event-name exemption trusts that a contract's event called
`supply` is not a Stellar Asset Contract event, which holds for every event name the SAC does not use.

**Configure and suppress**

Turn the rule off by leaving XDR102 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR102 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR103

**Unvalidated bytes or string into text storage.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | check utf8.ValidString and reject or strip NUL before storing as text, or store the bytes as bytea, hex or base64 |
| Default severity | error (`severity: {XDR103: …}` changes it) |
| Default rule set | yes |
| Guide | [Validated versus unvalidated fields](/hardening/overview) |
| Self-audit checklist item | HC-103 |
| Demonstrating corpus entry | `cap-0067/to-muxed-id-text-non-utf8-memo` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr103` |

**What it reports**

Bytes or a string that a submitter or a contract controls reach text storage without UTF-8 and NUL handling.

Sources are `xdr.Memo.Text` and its accessors, `ingest.LedgerTransaction.Memo()`, `xdr.ScVal.Str`,
`ScVal.ExecutableTag`, `ContractExecutableExternalRef.Tag`, `ScBytes`, `ManageDataOp.DataValue`,
`DataEntry.DataValue` and the text arm of a token transfer `MuxedInfo`. Text sinks are the arguments of
`database/sql` and `pgx` `Exec`, `Query` and `CopyFrom`, `string` struct fields tagged `db:"…"`, proto3 string
fields of the reader's own message types, and any field named in `sinkstext` (all errors), and `string` fields
tagged `json:"…"` (a warning: `encoding/json` writes invalid UTF-8 as U+FFFD and NUL as `\u0000`, so the
stored text silently differs from the bytes on chain, and a PostgreSQL `jsonb` column rejects the NUL).

Not sources: `SetOptionsOp.HomeDomain` and `ManageDataOp.DataName`, which stellar-core validates as printable
ASCII. `ScSymbol` is restricted by the host.

The report is silent after a dominating `utf8.ValidString` check together with a NUL check, after
`strings.ToValidUTF8` with NUL stripping, after base64 or hex encoding, after conversion to `[]byte` for a bytes
column, or after a configured sanitiser (`sanitizerstext`). A value that parsed as an integer
(`strconv.ParseUint`, `ParseInt`, `Atoi` with a nil error) or that a dominating comparison or `switch` fixed to
one of a few clean string literals carries no text either.

**Why it matters**

A text memo has only an XDR length bound: stellar-core accepts a memo that is not valid UTF-8 and copies it
verbatim into the transaction's events. An `ScString` is arbitrary bytes. PostgreSQL rejects invalid UTF-8 and
NUL in text columns, so one such value fails the whole persist transaction; for a reader that commits a ledger
at a time, that stops ingestion.

**Example**

Reported:

```go
// lint/testdata/xdr1xx/xdr103/bad.go
// (a) Memo text into a database/sql parameter.
func storeMemo(db *sql.DB, memo xdr.Memo) error {
	text, ok := memo.GetText()
	if !ok {
		return nil
	}
	_, err := db.Exec(`INSERT INTO memos (text) VALUES ($1)`, text)
	return err
}
```

Not reported:

```go
// lint/testdata/xdr1xx/xdr103/good.go
// (b) Invalid UTF-8 replaced and NUL bytes stripped.
func storeMemoSanitised(db *sql.DB, memo xdr.Memo) error {
	text := strings.ReplaceAll(strings.ToValidUTF8(memo.MustText(), "�"), "\x00", "")
	_, err := db.Exec(`INSERT INTO memos (text) VALUES ($1)`, text)
	return err
}
```

**Limits**

The analyzer cannot see SQL column types: a column that is really `bytea` is reported until it is configured or
the value is converted to `[]byte`. SQL built by string concatenation is not followed. Fields are followed one by
one through struct values and through struct pointers passed to or returned from functions of the same package (a
builder's methods); what a pointer field points to, and a callee's writes through a pointer, are not. A helper of the
same package called at several sites returns at each site only what that site passed in.

**Configure and suppress**

Turn the rule off by leaving XDR103 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR103 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).


### XDR105

**Must&lt;Arm>() on a multi-arm union without a dominating discriminant check.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | switch on the union's type, or use the ok result of Get&lt;Arm>(), before calling Must&lt;Arm>() |
| Default severity | warning (`severity: {XDR105: …}` changes it) |
| Default rule set | no: opt-in, add XDR105 to `rules` |
| Guide | [Validated versus unvalidated fields](/hardening/overview) |
| Self-audit checklist item | HC-107 |
| Demonstrating corpus entry | `cap-0067/token-events-bytes-and-bad-type-muxed-id` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr105` |

**What it reports**

`Must<Arm>()` on a union with more than one arm, at a point not dominated by a check of the same value's
discriminant (a `switch` on its type, a comparison, or the `ok` result of the matching `Get<Arm>()`).

**Why it matters**

The `Must…` accessors panic when the value holds another arm. Which arm a field of a ledger holds is chosen by the
submitter or a contract wherever the protocol allows several, so an unchecked `Must…` lets a ledger crash the
reader.

**Example**

Reported:

```go
// lint/testdata/xdr1xx/xdr105/bad.go
func memoText(m xdr.Memo) string {
	return m.MustText()
}
```

Not reported:

```go
// lint/testdata/xdr1xx/xdr105/good.go
func memoTextChecked(m xdr.Memo) string {
	if m.Type != xdr.MemoTypeMemoText {
		return ""
	}
	return m.MustText()
}
```

**Limits**

Opt-in, because the rule cannot know protocol facts that fix the arm (for example that a successful operation of
one type always has a result of the matching arm) and reports such calls too.

**Configure and suppress**

Turn the rule off by leaving XDR105 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR105 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](/reference/lint-rules#configuring-and-suppressing).
