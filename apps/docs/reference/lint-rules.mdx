## Running it

| Mode | How |
|---|---|
| Standalone | `go install github.com/OWNER/REPO/lint/cmd/xdrlint@<version>`, then `xdrlint ./...` in your module |
| `go vet` tool | `go vet -vettool=$(which xdrlint) ./...`; configuration from `.xdrlint.yml` or `XDRLINT_PROFILE`, `XDRLINT_CONFIG` |
| golangci-lint module plugin | a `.custom-gcl.yml` naming `github.com/OWNER/REPO/lint/plugin`, built with `golangci-lint custom` at the golangci-lint version that uses the same `golang.org/x/tools` (v2.15.0 for this release); settings under `linters.settings.custom.xdrlint.settings`: `profile`, `config`, or any configuration key inline. See the package documentation of `lint/plugin` |

Building `xdrlint` needs Go 1.26 or later; the code it checks may declare an older Go version.

A five-minute walk-through (install, run, read a diagnostic, suppress with a reason, run in CI) is in
[lint/README.md](/guides/lint-go).

Output:

| Flag | Output |
|---|---|
| (none) | text: `file:line:col: XDR201 (warning): message`, then a `fix:` line with the usual fix and a `docs:` line with the rule's page; on stderr a closing summary of what was found, whether the run fails and how to accept a report. Page links start at `-docs-base` (or `XDRLINT_DOCS_BASE`; default `lint/docs`; a base containing `{rule}` is a template) |
| `-json` | the `go/analysis` diagnostic tree with each report's rule, severity, function, guide anchor, corpus entry, fix and page link |
| `-sarif FILE` | SARIF 2.1.0, every rule linked to its page, suppressed reports marked as such |
| `-report FILE` | every report, suppressed ones included, as `xcc.report/v1` rows |
| `-expect FILE` | a comparison with a frozen expected list that fails on any difference in either direction. The list is compared by count: each entry (rule, file, function, suppressed) stands for `count` reports (default 1), so one report more than it counts is a difference |

| Exit | When |
|---|---|
| 0 | no unsuppressed report at or above `-fail-on`, and no `-expect` difference |
| 1 | an unsuppressed report that no `-pending` list names is at or above `-fail-on` (default `error`), or, with `-expect`, any difference |
| 2 | a usage, configuration or loading error; or no recognised source package is loaded (none of the packages, nor anything they import, is go-stellar-sdk's `xdr` package or an alias of it), since the rules then analyse nothing |

## Configuration

`.xdrlint.yml` in the module (or a file named with `-config`), over a shipped profile named with `-profile`
(`default`, `wallet-backend`, or a path). Keys are flat and lower-case so that golangci-lint can pass them through:

| Key | Meaning |
|---|---|
| `rules` | enabled rule IDs (default: every rule not marked opt-in) |
| `severity` | map of rule ID to `error`, `warning` or `info` |
| `xdrpackagealiases` | extra import paths treated as the SDK's `xdr` package |
| `participantnameregex` | names of participant sets (default `(?i)participant`) |
| `sinksparticipant`, `sinksaccountkey`, `sinkstext`, `sinksmovement` | extra sinks, as `pkg.Func`, `pkg.Type.Method` or `pkg.Type.Field` |
| `sanitizersaddress`, `sanitizerstext`, `sanitizersevent` | functions accepted as normalisers or verifiers |
| `budgetmethods` | methods accepted as a depth budget check (XDR201) |
| `overflowpolicy`, `overflowflags`, `haltingfuncs`, `ingestentrypoints` | what the project does at a bound (XDR206) |
| `floors` | map of structure to the minimum bound (XDR207) |
| `suppressions` | an external suppression file |

A configured name that does not exist in a loaded package stops the run, so a misspelt sink cannot silently check
nothing.


## Configuring and suppressing

Every report can be accepted with a reason:

- **Inline**, on the reported line or on the enclosing function's doc comment:
  `//xdrlint:ignore XDR201 linear walk over a tree the decoder bounded`. Under golangci-lint,
  `//nolint:xdrlint // <reason>` works too (enable `nolintlint` with `require-explanation` and
  `require-specific`).
- **An external suppression file**, for code you cannot edit: a YAML list of entries with `rule`, `file`
  (module-relative), one or more of `function` (`F` or `Type.Method`), `anchor` (a substring of the reported line),
  `line` (the reported line) and `message` (the report's message), and `reason`; optionally `finding`, `issue`,
  `commit`, `reviewer` and `date`. Every key given must match. An entry with a function only survives line drift
  but also accepts any new report of its rule in that function; an anchor or a line narrows it to one site, which
  is what a list frozen against one commit should use. `function` with `message` is the baseline key that
  survives code moving within the file: the message is compared without the line numbers it names
  (`line 28`, `events.go:12`), so it names one report without naming a line.


A suppression without a reason, one naming an unknown rule, and one that suppresses nothing are reported as
XDR000, which cannot itself be suppressed.

Every diagnostic names, in `assumption` (JSON, SARIF result properties and `-report` rows), the assumption about
the ledger the reported code makes, as a stable key such as `meta-version:v4-only` or `narrowing:u64->int64`.
`lint/docs/assumptions.md` lists every key with the input that violates it. Suppressed reports are not printed, but `-report`, `-json` and `-sarif`
keep them, marked as suppressed.


## Suppression hygiene

### XDR000

**Suppression without a reason, naming an unknown rule, or suppressing nothing.**


| | |
|---|---|
| Family | XDR0xx: suppression hygiene |
| How to fix | give the directive or entry a reason after the rule ID, name a rule that exists, or delete the suppression that matches nothing |
| Default severity | error (`severity: {XDR000: …}` changes it) |
| Default rule set | yes |
| Documentation | [Configuring and suppressing](#configuring-and-suppressing) |
| Fixtures | `lint/testdata/xdr0xx/xdr000` |

**What it reports**

A suppression that cannot be trusted:

- an inline directive (`//xdrlint:ignore`) with no reason, naming an unknown rule, malformed, or naming XDR000;
- an entry of an external suppression file with no reason, an unknown rule, none of a function, an anchor and a
  line, or an unknown key;
- any suppression, inline or external, that suppresses nothing.

**Why it matters**

A suppression is a reviewed statement that a report is understood. One without a reason cannot be reviewed, and
one that suppresses nothing has outlived the code it was written for. Reporting stale suppressions is what makes a
frozen suppression list able to fail: when the site changes or the rule stops firing, the run turns red.

**Example**

Reported:

```go
// lint/testdata/xdr0xx/xdr000/bad.go
func describe(tx xdr.TransactionEnvelope) []string {
	var names []string

	//xdrlint:ignore XDR201
	names = append(names, tx.SourceAccount().ToAccountId().Address())

	//xdrlint:ignore XDR999 not a rule of this linter
	names = append(names, tx.Memo().Type.String())

	// xdrlint:ignore XDR102 a space after the slashes would hide the directive

	//xdrlint:allow XDR102 wrong verb

	//xdrlint:ignore XDR000 hygiene is not optional

	//xdrlint:ignore XDR10 a typo

	return names
}
```

Not reported: a well-formed directive that marks a sink.

```go
// lint/testdata/xdr0xx/xdr000/good.go
// storeKey is an account-key sink; the directive is well formed and the key
// is reduced to the base account first.
//
//xdrlint:sink accountkey
func storeKey(keys map[string]bool, a xdr.MuxedAccount) {
	acc := a.ToAccountId()
	keys[acc.Address()] = true
}
```

**Limits**

XDR000 cannot itself be suppressed.

**Configure and suppress**

Turn the rule off by leaving XDR000 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR000 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](#configuring-and-suppressing).


## Mistake 1: trusting fields stellar-core does not validate

### XDR101

**Address built from a memo.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | route only a u64 to_muxed_id (or a MEMO_ID) into a muxed address; keep memo text and hash as data, never as an ID |
| Default severity | error (`severity: {XDR101: …}` changes it) |
| Default rule set | yes |
| Guide | [The event routing ID](/hardening/overview) |
| Self-audit checklist item | HC-101 |
| Demonstrating corpus entry | `cap-0067/to-muxed-id-text-from-memo` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr101` |

**What it reports**

A value derived from a transaction memo reaches the construction of a muxed address: an
`xdr.MuxedAccountMed25519`, `xdr.MuxedEd25519Account` or `xdr.MuxedContract` literal, `strkey.MuxedAccount.SetID`,
`strkey.MuxedContract.SetID`, `strkey.Encode` with a muxed version byte, `xdr.NewMuxedAccount` or
`xdr.MuxedAccountFromAccountId`.

Sources are the memo accessors (`xdr.Memo.Id`, `Text`, `Hash`, `RetHash` and their `Get…`/`Must…` forms,
`TransactionEnvelope.Memo()`, `ingest.LedgerTransaction.Memo()`), the token transfer processor's `MuxedInfo`
getters, and any value assigned on a path where a type switch chose the text or hash arm of a `MuxedInfo`.

**Why it matters**

stellar-core never checks what a memo contains, and since CAP-67 it copies the memo of a classic payment into
the event's `to_muxed_id`, which can therefore be a 64-bit ID, a text string or 32 bytes. A text or hash memo is
not a routing ID, and an address built from one names an account that nobody controls. Store a memo-derived ID
as an ID, next to the base account, and never turn it into an `M…` address.

**Example**

Reported:

```go
// lint/testdata/xdr1xx/xdr101/bad.go
// (b) A type switch whose text and hash arm sets id = 0 and falls through
// to SetID.
func destinationFromSwitch(to string, info *token_transfer.MuxedInfo) (string, error) {
	var id uint64
	switch c := info.Content.(type) {
	case *token_transfer.MuxedInfo_Id:
		id = c.Id
	case *token_transfer.MuxedInfo_Text, *token_transfer.MuxedInfo_Hash:
		id = 0
	default:
		return "", nil
	}
	var m strkey.MuxedContract
	if err := m.SetContractID(to); err != nil {
		return "", err
	}
	m.SetID(id)
	return m.Address()
}
```

Not reported: the ID is stored as an ID.

```go
// lint/testdata/xdr1xx/xdr101/good.go
// (a) The memo-derived routing ID stored only as an ID, never as an address.
func setToMuxedID(t *transfer, info *token_transfer.MuxedInfo) {
	if info == nil {
		return
	}
	switch c := info.Content.(type) {
	case *token_transfer.MuxedInfo_Id:
		id := c.Id
		t.ToMuxedID = &id
	case *token_transfer.MuxedInfo_Text, *token_transfer.MuxedInfo_Hash:
		// A memo, not a routing ID: not stored as one.
	}
}
```

**Limits**

A memo copied into a struct field and encoded into an address in another package is not followed. An indexer
that deliberately renders memo-routed addresses for display should suppress the report with that reason.

**Configure and suppress**

Turn the rule off by leaving XDR101 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR101 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](#configuring-and-suppressing).


### XDR102

**Unnormalised address used as an identity key.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | key on the base account: MuxedAccount.ToAccountId(), or a switch on ScAddress.Type that handles the muxed, claimable-balance and pool kinds |
| Default severity | error (`severity: {XDR102: …}` changes it) |
| Default rule set | yes |
| Guide | [Muxed and signed-payload handling](/hardening/overview) |
| Self-audit checklist item | HC-102 |
| Demonstrating corpus entry | `cap-0027/muxed-source-and-destination-max-ids` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr102` |

**What it reports**

An address string taken from a value that can be muxed, a signed payload, or a non-account kind is used as a
participant or account key without being reduced to its base account or having its kind checked.

Sources are `(*xdr.MuxedAccount).Address()` and `GetAddress()` (also through `TransactionEnvelope.SourceAccount()`,
`FeeBumpAccount()`, `Operation.SourceAccount` and operation destinations), `ingest.LedgerTransaction.AccountMuxed()`
and `FeeAccountAddress()`, `xdr.ScAddress.String()`, `(*xdr.SignerKey).Address()` and the keys of
`AccountEntry.SignerSummary()`. Sinks are participant sets and configured account-key types and functions
(`sinksparticipant`, `sinksaccountkey`).

An address can be wrong in two ways, and each is checked on its own: it can be in muxed form (`M…`, `W…`), or it
can be of a kind that is not an account (`B…` claimable balance, `L…` liquidity pool, `P…`, `T…`, `X…` signers).

The report is silent when the value went through `MuxedAccount.ToAccountId()`, when a dominating switch or `if` on
`ScAddress.Type` handles the muxed kinds and excludes or routes the claimable-balance and liquidity-pool kinds,
when a configured normaliser (`sanitizersaddress`) produced it, or when the address is the contract of a contract
data entry the host wrote into meta (never a muxed kind). Besides:

- **A sink that normalises.** An account-key type whose own `Value()` decodes the strkey, reduces the muxed
  account kind and refuses any payload that is not a 32-byte key (as `AddressBytea.Value()` does) stores a muxed
  address as its base key; so does a function whose string parameter only becomes such a type (a builder's
  `WithAccount`). Only the non-account kinds are reported there, because that type refuses them with a write
  error. The property is read from the `Value()` body, in whichever package declares it.
- **A re-parse of the same entry.** A sink on the passing branch of `sac.ContractBalanceFromContractData(entry, …)`
  (ok only when the balance key's holder is a contract) is kind-checked, when the address was read from the same
  ledger entry.
- **Contract storage.** The host refuses to store a claimable-balance, liquidity-pool or muxed address, so an
  address read from the key or value of a contract-data entry is a `G…` or `C…` address. This is decided per call
  of a shared helper: `addrString(entry.Key)` is exempt, `addrString(topics[1])` is not.
- **Where `B…` and `L…` come from.** A contract can never store, return or emit a claimable-balance or pool
  address: the host refuses to convert one to a contract value. Such an address reaches a reader only in events the
  host emits for the Stellar Asset Contract, or in the envelope (invocation arguments, the authorization tree), which
  is submitter bytes. The non-account kind is reported only for an address that may have been read from a contract
  event's topics or data or from those envelope fields, and not for one decoded on the branch where the event's name
  is one the Stellar Asset Contract never emits (`case "supply": decode(topics)`).

**Why it matters**

stellar-core uses only the ed25519 key of a muxed account; the 64-bit ID is never validated. Storing the `M…`
form as identity splits one account into as many accounts as there are IDs, and fixed-width columns truncate
`M…`, `P…` and `B…` strkeys. `ScAddress.String()` renders every kind SEP-23 defines, including claimable
balances (`B…`) and liquidity pools (`L…`), which are not accounts at all.

**Example**

Reported: the operation source is used as identity in its muxed form.

```go
// lint/testdata/xdr1xx/xdr102/bad.go
// (a) The operation source rendered with Address(): M… when muxed.
func operationParticipants(op xdr.Operation, participants set) {
	participants.Add(op.SourceAccount.Address())
}
```

Not reported:

```go
// lint/testdata/xdr1xx/xdr102/good.go
// (a) Reduced to the base account first.
func operationParticipantsBase(op xdr.Operation, tx *ingest.LedgerTransaction, participants set) {
	if op.SourceAccount != nil {
		participants.Add(op.SourceAccount.ToAccountId().Address())
	}
	participants.Add(tx.Envelope.SourceAccount().ToAccountId().Address())
	if acc, err := tx.Account(); err == nil {
		participants.Add(acc)
	}
}
```

**Limits**

Flows through `map[string]interface{}` are not followed. Sinks in another module are seen only when configured.
Values decoded from bytes (an RPC response, base64 topics) are not recognised as events or envelope fields, so an
address read from them loses the non-account-kind aspect (a false negative). The event-name exemption trusts that a contract's event called
`supply` is not a Stellar Asset Contract event, which holds for every event name the SAC does not use.

**Configure and suppress**

Turn the rule off by leaving XDR102 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR102 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](#configuring-and-suppressing).


### XDR103

**Unvalidated bytes or string into text storage.**


| | |
|---|---|
| Family | XDR1xx: trusting unvalidated fields |
| How to fix | check utf8.ValidString and reject or strip NUL before storing as text, or store the bytes as bytea, hex or base64 |
| Default severity | error (`severity: {XDR103: …}` changes it) |
| Default rule set | yes |
| Guide | [Validated versus unvalidated fields](/hardening/overview) |
| Self-audit checklist item | HC-103 |
| Demonstrating corpus entry | `cap-0067/to-muxed-id-text-non-utf8-memo` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr1xx/xdr103` |

**What it reports**

Bytes or a string that a submitter or a contract controls reach text storage without UTF-8 and NUL handling.

Sources are `xdr.Memo.Text` and its accessors, `ingest.LedgerTransaction.Memo()`, `xdr.ScVal.Str`,
`ScVal.ExecutableTag`, `ContractExecutableExternalRef.Tag`, `ScBytes`, `ManageDataOp.DataValue`,
`DataEntry.DataValue` and the text arm of a token transfer `MuxedInfo`. Text sinks are the arguments of
`database/sql` and `pgx` `Exec`, `Query` and `CopyFrom`, `string` struct fields tagged `db:"…"`, proto3 string
fields of the reader's own message types, and any field named in `sinkstext` (all errors), and `string` fields
tagged `json:"…"` (a warning: `encoding/json` writes invalid UTF-8 as U+FFFD and NUL as `\u0000`, so the
stored text silently differs from the bytes on chain, and a PostgreSQL `jsonb` column rejects the NUL).

Not sources: `SetOptionsOp.HomeDomain` and `ManageDataOp.DataName`, which stellar-core validates as printable
ASCII. `ScSymbol` is restricted by the host.

The report is silent after a dominating `utf8.ValidString` check together with a NUL check, after
`strings.ToValidUTF8` with NUL stripping, after base64 or hex encoding, after conversion to `[]byte` for a bytes
column, or after a configured sanitiser (`sanitizerstext`). A value that parsed as an integer
(`strconv.ParseUint`, `ParseInt`, `Atoi` with a nil error) or that a dominating comparison or `switch` fixed to
one of a few clean string literals carries no text either.

**Why it matters**

A text memo has only an XDR length bound: stellar-core accepts a memo that is not valid UTF-8 and copies it
verbatim into the transaction's events. An `ScString` is arbitrary bytes. PostgreSQL rejects invalid UTF-8 and
NUL in text columns, so one such value fails the whole persist transaction; for a reader that commits a ledger
at a time, that stops ingestion.

**Example**

Reported:

```go
// lint/testdata/xdr1xx/xdr103/bad.go
// (a) Memo text into a database/sql parameter.
func storeMemo(db *sql.DB, memo xdr.Memo) error {
	text, ok := memo.GetText()
	if !ok {
		return nil
	}
	_, err := db.Exec(`INSERT INTO memos (text) VALUES ($1)`, text)
	return err
}
```

Not reported:

```go
// lint/testdata/xdr1xx/xdr103/good.go
// (b) Invalid UTF-8 replaced and NUL bytes stripped.
func storeMemoSanitised(db *sql.DB, memo xdr.Memo) error {
	text := strings.ReplaceAll(strings.ToValidUTF8(memo.MustText(), "�"), "\x00", "")
	_, err := db.Exec(`INSERT INTO memos (text) VALUES ($1)`, text)
	return err
}
```

**Limits**

The analyzer cannot see SQL column types: a column that is really `bytea` is reported until it is configured or
the value is converted to `[]byte`. SQL built by string concatenation is not followed. Fields are followed one by
one through struct values and through struct pointers passed to or returned from functions of the same package (a
builder's methods); what a pointer field points to, and a callee's writes through a pointer, are not. A helper of the
same package called at several sites returns at each site only what that site passed in.

**Configure and suppress**

### XDR105

**Must&lt;Arm>() on a multi-arm union without a dominating discriminant check.**


| | |

## Mistake 2: no depth or size cap on recursive structures

### XDR201

**Recursion over a self-referential xdr type with no depth bound.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | pass a depth counter down the recursion and stop at a limit at or above what stellar-core admits |
| Default severity | warning (`severity: {XDR201: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-201 |
| Fixtures | `lint/testdata/xdr2xx/xdr201` |

**What it reports**

A function or closure that recurses, directly or through other functions of the same package, passing a value of a
self-referential xdr type (after dereference, slice element or range element), with no depth bound. The
self-referential types are computed from the loaded `xdr` package: `SorobanAuthorizedInvocation`,
`SorobanDelegateSignature`, the `ScVal` group, `ClaimPredicate` and the `ScSpecTypeDef` group at go-stellar-sdk
v0.9.0. The report is an error when a level merges its children's results (`Union`, `append(x, ys...)`), and a
warning otherwise.

A bound is an integer parameter, receiver field or captured variable that every recursive call changes by a
constant and that is compared with a limit before recursing, leading to a return or break; or a configured budget
method (`budgetmethods`) called and error-checked first.

**Why it matters**

The host checks only the authorization entries that a `require_auth` call matched. Unmatched entries, nested trees included, are never examined, and a transaction carrying them succeeds, so the shape of the tree is the submitter's choice.

A bound silences this rule only. A constant bound on a path fed from ledger meta is then examined by XDR207, which
reports it when it is below what stellar-core admits, and the behaviour past the bound by XDR206. A low fixed cap
is never the quiet option.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr201/bad.go
// (a) A named function over SubInvocations.
func countContracts(inv xdr.SorobanAuthorizedInvocation) int {
	n := 0
	if inv.Function.Type == xdr.SorobanAuthorizedFunctionTypeSorobanAuthorizedFunctionTypeContractFn {
		n++
	}
	for _, sub := range inv.SubInvocations {
		n += countContracts(sub)
	}
	return n
}
```

Not reported: the depth limit comes from configuration.

```go
// lint/testdata/xdr2xx/xdr201/good.go
// (a) A depth parameter compared with a bound from configuration.
func walkBounded(cfg config, inv xdr.SorobanAuthorizedInvocation, depth int) error {
	if depth > cfg.MaxAuthDepth {
		return errTooDeep
	}
	for _, sub := range inv.SubInvocations {
		if err := walkBounded(cfg, sub, depth+1); err != nil {
			return err
		}
	}
	return nil
}
```

**Limits**

"The walk only runs for successful transactions" is deliberately not a bound. Recursion through interface
dispatch, through `fmt` and `Stringer` (`ScVal.String`), or across packages is not seen. Walkers over structures
that stellar-core bounds itself (`ClaimPredicate`, at most 4 levels) are reported and can be suppressed with that
reason.

### XDR202

**Iterative walker with an unbounded worklist.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | count nodes (or the worklist length) inside the loop and stop at a limit at or above what stellar-core admits |
| Default severity | warning (`severity: {XDR202: …}` changes it) |
| Default rule set | yes |
| Guide | [Recommendations for meta readers](/hardening/overview) |
| Self-audit checklist item | HC-202 |
| Fixtures | `lint/testdata/xdr2xx/xdr202` |

**What it reports**

A loop that pops values of a self-referential xdr type from a slice and appends their children, with no comparison
of the worklist length or of a counter incremented in the loop against a bound.

**Why it matters**

Rewriting a recursive walk as a loop with an explicit stack removes the recursion but not the problem: the work
still grows with a tree the submitter shaped (see XDR201). The bound has to be there in either form.

**Example**

Reported:

```go
// lint/testdata/xdr2xx/xdr202/bad.go

		stack = stack[:len(stack)-1]

		}
		stack = append(stack, inv.SubInvocations...)
	}
	return out
}
```

```go
// lint/testdata/xdr2xx/xdr202/good.go
// An explicit stack with a node counter and a length check.
func contractsBounded(root xdr.SorobanAuthorizedInvocation, maxNodes int) ([]string, error) {
	var out []string
	stack := []xdr.SorobanAuthorizedInvocation{root}
	visited := 0
	for len(stack) > 0 {
		visited++
		if visited > maxNodes || len(stack) > maxNodes {
			return nil, errTooMany
		}
		inv := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		if fn, ok := inv.Function.GetContractFn(); ok {
			s, _ := fn.ContractAddress.String()

		}

```

### XDR203

**Decoded integer used as an allocation size or loop bound.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |

### XDR206

**Behaviour at a bound differs from the declared overflow policy.**


| | |
|---|---|
| Family | XDR2xx: missing depth and size caps |
| How to fix | make the branch past the bound do what overflowpolicy declares (fail the ledger, or skip and set the flag); never exit the process |
| Default severity | warning (`severity: {XDR206: …}` changes it) |
| Default rule set | yes |
| Guide | [What to do at a bound: a trade-off](/hardening/overview) |
| Self-audit checklist item | HC-205 |
| Fixtures | `lint/testdata/xdr2xx/xdr206` |

**What it reports**

For a walk that has a bound (XDR201 or XDR202 accepted it), the branch taken past the bound does something other
than what the project declared in `overflowpolicy`:

- under any policy, it ends the process: `panic`, `log.Fatal…`, `os.Exit` or a configured `haltingfuncs` entry;
- under `halt-ledger`, it returns without an error (`return nil`, `continue`, `break`), silently truncating;
- under `skip-and-flag`, it returns or continues without setting one of the configured `overflowflags`.

With no policy declared only the first case is reported, and the message asks for a declaration.

**Why it matters**

Past a bound a reader of ledger meta has two defensible choices, and both cost something. Stopping the ledger
with a typed, alertable error stores nothing wrong but leaves ingestion stopped on a ledger stellar-core accepted
until the bound is raised. Skipping the field, flagging the record as incomplete and keeping the raw XDR keeps
ingestion up but leaves the record incomplete until it is re-derived. A crash is neither, and a silent truncation
is the partial drop no reader wants. The linter checks that the code does what was declared; it does not choose.

**Example**

Reported under any policy:

```go
// lint/testdata/xdr2xx/xdr206/xdr206.go
func walkPanics(l limits, inv xdr.SorobanAuthorizedInvocation, depth int) {
	if depth > l.MaxAuthDepth {
		panic("auth tree too deep")
	}
	for _, sub := range inv.SubInvocations {
		walkPanics(l, sub, depth+1)
	}
}
```

Compliant under `halt-ledger`:

```go
// lint/testdata/xdr2xx/xdr206/xdr206.go
// Without a declared policy, stopping with an error and skipping are both
// left alone.
func walkError(l limits, inv xdr.SorobanAuthorizedInvocation, depth int) error {
	if depth > l.MaxAuthDepth {
		return errTooDeep
	}
	for _, sub := range inv.SubInvocations {
		if err := walkError(l, sub, depth+1); err != nil {
			return err
		}
	}
	return nil
}
```

**Limits**

Whether an error returned under `halt-ledger` really stops the ledger, or a caller swallows it, is not decided
locally.

## Mistake 3: participants from the envelope instead of the meta

### XDR301

**Participants harvested from the authorization tree or invocation arguments.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |
| How to fix | take participants from meta (entry changes, nonce entries, events of a verified contract), not from the authorization tree or call arguments |
| Default severity | error (`severity: {XDR301: …}` changes it) |
| Default rule set | yes |
| Guide | [Participants from meta](/hardening/overview) |
| Self-audit checklist item | HC-301 |
| Demonstrating corpus entry | `cap-0046/auth-unmatched-entries-succeed` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr3xx/xdr301` |

**What it reports**

A value read from an authorization entry or from invocation arguments reaches a participant sink (or a configured
state-change sink) without corroboration from meta. Sources are the credential addresses of
`SorobanAuthorizationEntry`, delegate addresses, `RootInvocation` and `SubInvocations`, the contract address and
create-contract preimages of a `SorobanAuthorizedFunction`, `InvokeContractArgs.ContractAddress` and `Args`, and
create-contract preimages.

The report is silent when the value is used only as a key into, or compared with, a set built from meta, and the
sink depends on that membership test.

**Why it matters**

The host authenticates only the authorization entries a `require_auth` call matched; a successful transaction can
carry any number of others, naming any address. The proof that an address authorised an operation is the nonce
entry the host wrote for it in the meta. A reader that adds every address in the tree lets a submitter write into
anyone's history.

**Example**

Reported:

```go
// lint/testdata/xdr3xx/xdr301/bad.go
// (a) A credential address goes straight into the participant set.
func credentialParticipants(tx ingest.LedgerTransaction, entries []xdr.SorobanAuthorizationEntry) addrSet {
	participants := addrSet{}
	_ = tx.GetFeeChanges()
	for _, e := range entries {
		if e.Credentials.Type != xdr.SorobanCredentialsTypeSorobanCredentialsAddress {
			continue
		}
		addr, err := e.Credentials.MustAddress().Address.String()
		if err != nil {
			continue
		}
		participants.Add(addr)
	}
	return participants
}
```

Not reported: authorizers come from the nonce entries in meta.

```go
// lint/testdata/xdr3xx/xdr301/good.go
// (a) Authorizers are the owners of the nonce entries the host created.
func authorizers(tx ingest.LedgerTransaction, opIndex uint32) (addrSet, error) {
	participants := addrSet{}
	changes, err := tx.GetOperationChanges(opIndex)
	if err != nil {
		return nil, err
	}
	for _, c := range changes {
		if c.Type != xdr.LedgerEntryTypeContractData || c.Post == nil {
			continue
		}
		cd := c.Post.Data.MustContractData()
		if cd.Key.Type != xdr.ScValTypeScvLedgerKeyNonce {
			continue
		}
		a, err := cd.Contract.String()
		if err != nil {
			return nil, err
		}
		participants.Add(a)
	}
	return participants, nil
}
```

**Limits**

An indexer that deliberately keeps "declared, unverified" relations apart from participants should suppress the
report with that reason. The host also requires authorization for some top-level host functions (a deploy from an
address). When the operation's own host function and the authorization tree reach the same sink through a function
value (a callback both paths call), the rule's source is type-based and cannot tell them apart: that report is a

### XDR302

**Envelope operation fields used as participants without a success gate.**


| | |
|---|---|
| Family | XDR3xx: participants from the envelope instead of the meta |

**What it reports**

(`LedgerTransaction.Successful()`, `TransactionResult(Pair).Successful()`, or a variable holding one). A helper

source are always participants. Operation accounts are participants only when the operation was applied: a

## Beyond the three: assumptions about the ledger's form, ranges and outcomes

### XDR401

**One meta version assumed: an arm read without a version check, or a version check that halts on the others.**


| | |
|---|---|
| Family | XDR4xx: assumptions about the ledger's form, ranges and outcomes |
| How to fix | switch on the meta's V and handle every version the SDK declares (or skip the transaction with a typed, logged reason); never Must&lt;Vn>() or .Vn without that switch |
| Default severity | error (`severity: {XDR401: …}` changes it) |
| Default rule set | yes |
| Guide | [Fail closed at protocol boundaries](/hardening/overview) |
| Self-audit checklist item | HC-506 |
| Demonstrating corpus entry | `ledger/meta-profile-default-flags-txmeta-v3` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr4xx/xdr401` |

**What it reports**

Code that assumes one version of a versioned meta union, `xdr.TransactionMeta` or `xdr.LedgerCloseMeta`:

- an arm read with no version check of the same value: `meta.MustV3()`, `tx.UnsafeMeta.V4.SorobanMeta`, `lcm.V1`,
  where no enclosing or earlier `if` or `switch` tests `meta.V`, `meta.GetV3()` or a variable bound to them;
- a version check that halts the job on the versions it does not accept: `if meta.V != 4 { return err }`,
  `if lcm.V != 1 { panic(…) }`, or a `switch meta.V` whose default returns an error or panics, when the accepted
  versions leave out a version the rule takes as emitted by a current stellar-core (TransactionMeta v2–v4,
  LedgerCloseMeta v0–v2; see Limits).

The message names the versions that halt the job. A `switch` that handles every version the SDK declares and
stops above them with a typed error is the reviewed-version policy and is not reported. Writes to an arm (a test
helper building meta) are not reads.

**Why it matters**

Which meta version a reader receives depends on where its ledgers come from, not only on the protocol. The public
data lake serves TransactionMeta v4 for all of history; captive core and older datastores emit v2 for ledgers
before protocol 20 and v3 for protocols 20 to 22, and LedgerCloseMeta v0 before protocol 20. A reader tested on
one source stops on the first ledger from another: `export_token_transfer` failing with "expected version 4 got
3" is this mistake. A later protocol can add a version too.

**Example**

Reported:

```go
// lint/testdata/xdr4xx/xdr401/bad.go
// (c) A version check that halts on every other version (the export dies on
// older meta).
func unifiedEvents(tx ingest.LedgerTransaction) ([]xdr.TransactionEvent, error) {
	version := tx.UnsafeMeta.V
	if version != 4 {
		return nil, fmt.Errorf("expected meta version 4, got %d", version)
	}
	return tx.UnsafeMeta.MustV4().Events, nil
}
```

Not reported:

```go
// lint/testdata/xdr4xx/xdr401/good.go

// policy (stop with a typed error above what was reviewed).
func txChangesAfterAll(meta xdr.TransactionMeta) (xdr.LedgerEntryChanges, error) {
	switch meta.V {
	case 0:
		return nil, nil
	case 1:
		return nil, nil
	case 2:
		return meta.MustV2().TxChangesAfter, nil
	case 3:
		return meta.MustV3().TxChangesAfter, nil
	case 4:
		return meta.MustV4().TxChangesAfter, nil
	default:
		return nil, fmt.Errorf("meta version %d is above the reviewed versions", meta.V)
	}
}
```

**Limits**

The check is matched by how the value is written (`tx.UnsafeMeta`), within one function: a check made by the
caller before it passes the meta on is not seen. An else-if chain (`GetV1`, then `GetV2`, then `V == 0`, else
an error) is not judged. The rule assumes that a current stellar-core emits TransactionMeta v2 to v4 and
LedgerCloseMeta v0 to v2, and treats TransactionMeta v0 and v1 as historical forms: a check that rejects only
them is not reported. That table is an assumption of the rule, not a statement checked against stellar-core. Files of test support code (names
containing `test` or `mock`, integration-test and load-test directories) are skipped.

### XDR402

**Wide integer narrowed without a range check and stored.**


| | |
|---|---|
| Family | XDR4xx: assumptions about the ledger's form, ranges and outcomes |
| How to fix | keep the full width (uint64, a decimal string or NUMERIC column, big.Int), or compare with the target type's bounds and reject the value before converting |
| Default severity | error (`severity: {XDR402: …}` changes it) |
| Default rule set | yes |
| Guide | [64-bit IDs](/hardening/overview) |
| Self-audit checklist item | HC-404 |
| Demonstrating corpus entry | `cap-0027/muxed-source-id-above-2-pow-63` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr4xx/xdr402` |

**What it reports**

A conversion that cannot hold every value of a ledger integer, whose result is stored:

- `uint64` (muxed IDs, offer IDs, time bounds, sequence ages: `xdr.Uint64`, `xdr.TimePoint`, `xdr.Duration`)
  to `int64`, `int`, a 32-bit or smaller type, or `float64`;
- `int64` to `int32` or smaller; `uint32` or `int32` to `int16` or smaller;
- `(*big.Int).Int64()` or `Uint64()` without a dominating `IsInt64()`, `IsUint64()`, `BitLen()` or `Cmp()` on the
  same value (an i128 amount narrowed to 64 bits);
- `strconv.ParseFloat` of a token amount read from an SDK field or method (an i128 rounded to `float64`, a
  warning).

The value must be computed from the ledger: on the way back through arithmetic, conversions, loads and field
reads, a named integer type of the SDK's `xdr` package, an integer field of an SDK struct, or the result of an
SDK function. Stored means written to a struct field, a map, a slice element or an escaping variable, appended,
or passed to a database call or a builder (`With…`, `Set…`, `Add…`), possibly after more arithmetic or a
conversion to text or a nullable wrapper (`null.IntFrom`). A relational comparison (`<`, `<=`, `>`, `>=`) of the
value, or of a value it was computed from, with a constant that dominates the conversion counts as a range check;
a nil or equality check does not. Ledger close times stellar-core writes (`SeqTime`, `CloseTime`) are not
reported, nor is a minimum sequence age (`PreconditionsV2.MinSeqAge`, `TransactionEnvelope.MinSeqAge()`) stored in
a 64-bit type: stellar-core admits a transaction only while that age is at most the ledger's close time
(`txBAD_MIN_SEQ_AGE_OR_GAP`), so no value in a ledger reaches 2^63. `uint32` to `int32` is not reported: ledger sequences and
indexes stay far below 2^31.

**Why it matters**

The ledger's integers are wider than many readers' columns. Muxed IDs reach 2^64−1 on mainnet, SAC balances above
2^63 exist, and a `uint64` written to a signed 64-bit warehouse column made a load reject tens of thousands of rows.
A narrowing conversion does not fail: it stores a negative or rounded number that looks real.

**Example**

Reported:

```go
// lint/testdata/xdr4xx/xdr402/bad.go
// (a) A muxed ID into a signed 64-bit column: an ID ≥ 2^63 is stored
// negative.

	row.SellerMuxedID = int64(m.Id)
}
```

Not reported:

```go

func muxedIDChecked(m xdr.MuxedAccountMed25519, row *txRow) bool {
	if uint64(m.Id) > math.MaxInt64 {
		return false
	}
	row.SellerMuxedID = int64(m.Id)
	return true
}
```

**Limits**

A value taken out of an `interface{}` (a details map) is not followed. A result returned to the caller and stored
there is not followed. A range check is any dominating comparison with a constant, not one that proves the bound.
Splitting a big integer into 64-bit halves after `Rsh` or `And` is not reported.

| How to fix | build rows from diagnostic events only after LedgerTransaction.Successful(); attribute to an operation only its own changes (GetOperationChanges), never the fee or transaction-level changes |
| Default severity | error (`severity: {XDR405: …}` changes it) |
| Default rule set | yes |
| Guide | [Failed transactions: what still lands in the ledger](/hardening/overview) |
| Self-audit checklist item | HC-307 |
| Demonstrating corpus entry | `cap-0046/failed-soroban-tx-with-sac-transfers-in-diagnostics` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr4xx/xdr405` |

**What it reports**

Rows built from meta that does not mean what the row says:

- `LedgerTransaction.GetDiagnosticEvents()`, or a `DiagnosticEvents` field of the SDK's meta and event types,
  feeding rows with no success check (`Successful()`, `TransactionResultCodeTxSuccess`, a variable holding one) in
  the function or in every same-package caller (an error);
- `LedgerTransaction.GetChanges()` or the `TxChangesBefore`/`TxChangesAfter` fields read in a function that works
  on one operation (an integer parameter named like an operation index, or an operation wrapper type) and feeding
  rows (a warning).

Feeding rows means the value, or a value ranged or derived from it, is used in a composite literal, appended,
assigned to a field or map entry, or passed to a same-package function in such a position. Not reported: a
function whose rows record the transaction's success (it, or a same-package function it calls, reads
`Successful()`), and an accessor that copies the events into a `DiagnosticEvents` field.

**Why it matters**

A failed Soroban transaction still carries the diagnostic events of the calls that ran before it failed, some with
`InSuccessfulContractCall` set, but the transaction rolled them back. Rows built from them describe transfers that
never happened. `GetChanges()` holds the fee, sequence-number and transaction-level changes as well as every
operation's, so reading it for one operation attributes changes the operation did not make.

**Example**

Reported:

```go
// lint/testdata/xdr4xx/xdr405/bad.go
// (a) Rows from diagnostic events with no success gate here or in the
// caller: a failed transaction's rolled-back calls become balance changes.
func balanceChanges(tx ingest.LedgerTransaction) ([]balanceChange, error) {
	events, err := tx.GetDiagnosticEvents()
	if err != nil {
		return nil, err
	}
	var out []balanceChange
	for _, ev := range events {
		if !ev.InSuccessfulContractCall {
			continue
		}
		out = append(out, balanceChange{Event: ev.Event})
	}
	return out, nil
}
```

Not reported:

```go
// lint/testdata/xdr4xx/xdr405/good.go
// The caller gates on success.
func balanceChangesGated(tx ingest.LedgerTransaction) ([]balanceChange, error) {
	events, err := tx.GetDiagnosticEvents()
	if err != nil {
		return nil, err
	}
	var out []balanceChange
	for _, ev := range events {
		out = append(out, balanceChange{Event: ev.Event})
	}
	return out, nil
}
```

**Limits**

Callers are followed within the package, up to four levels. Operation scope is read from parameter names and
types.

**Configure and suppress**

Turn the rule off by leaving XDR405 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR405 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](#configuring-and-suppressing).


### XDR406

**Closed switch over an xdr enum that writes rows, with no default or a panicking default.**


| | |
|---|---|
| Family | XDR4xx: assumptions about the ledger's form, ranges and outcomes |
| How to fix | add a default that records the unknown value (a counter, a typed skip, an error the operator sees) without halting, and handle every value the SDK declares |
| Default severity | warning (`severity: {XDR406: …}` changes it) |
| Default rule set | no: opt-in, add XDR406 to `rules` |
| Guide | [Fail closed at protocol boundaries](/hardening/overview) |
| Self-audit checklist item | HC-507 |
| Demonstrating corpus entry | `cap-0088/first-ledger-with-signed-ms` (registered in `corpus/plan.json`) |
| Fixtures | `lint/testdata/xdr4xx/xdr406` |

**What it reports**

A `switch` over an enum of the SDK's `xdr` package (`OperationType`, `LedgerEntryType`, `ScValType`, …) whose
cases write rows (append, assign to a field or map entry, build a composite literal, call a builder or database
method) and that has no default, or a default that panics or exits. The message lists the values the SDK declares
that the switch does not handle; when it handles all of them, a value a later protocol adds still falls through.

This rule is opt-in.

**Why it matters**

Protocol upgrades add enum values: operations, entry types, value types, address kinds. A closed switch drops the
new value without a trace, or halts the job on it, on upgrade day. A default that records the unknown value (an
error the operator sees, a counter, a typed skip) turns a silent loss into a decision.

**Example**

Reported:

```go
// lint/testdata/xdr4xx/xdr406/bad.go
// (b) A panicking default: a new value stops the job.
func memoRow(m xdr.Memo) row {
	switch m.Type {
	case xdr.MemoTypeMemoNone, xdr.MemoTypeMemoText, xdr.MemoTypeMemoId, xdr.MemoTypeMemoHash, xdr.MemoTypeMemoReturn:
		return row{Kind: m.Type.String()}
	default:
		panic("unknown memo type")
	}
}
```

Not reported:

```go
// lint/testdata/xdr4xx/xdr406/good.go
// A default that reports the unknown value without halting.
func memoRowChecked(m xdr.Memo) (row, error) {
	switch m.Type {
	case xdr.MemoTypeMemoNone, xdr.MemoTypeMemoText, xdr.MemoTypeMemoId, xdr.MemoTypeMemoHash, xdr.MemoTypeMemoReturn:
		return row{Kind: m.Type.String()}, nil
	default:
		return row{}, fmt.Errorf("unknown memo type %d", m.Type)
	}
}
```

**Limits**

Many switches handle a subset on purpose (only the entry types a table holds). The rule cannot tell that from an
omission, which is why it is opt-in.

**Configure and suppress**

Turn the rule off by leaving XDR406 out of `rules` in `.xdrlint.yml` or a profile. To accept one report, put `//xdrlint:ignore XDR406 <reason>` on the reported line or on the enclosing function's doc comment (under golangci-lint, `//nolint:xdrlint // <reason>`), or add an entry to an external suppression file for code you cannot edit. A suppression needs a reason, and one that suppresses nothing is itself reported (XDR000). See [Configuring and suppressing](#configuring-and-suppressing).
