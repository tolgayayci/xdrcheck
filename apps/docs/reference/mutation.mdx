For SDK and indexer maintainers who want inputs beyond the corpus: `xdrcheck mutate` takes real corpus values,
mutates them at the type level, runs every mutant through every conformance column and replay adapter, and reports
where a reader disagrees with the oracle, with stellar-core, or with the other readers. It runs offline and is
reproducible: the bytes of a mutant are a pure function of the source entry, the seed, the mutator and the place it
acts on.

The work is split in two:

| Part | What it does |
|---|---|
| `xdrcheck-mutate` (Rust, `crates/xdrcheck-mutate`) | Reads corpus values with a schema-driven reader built from the pinned `stellar-xdr` crate's own XDR definitions, keeping every node's byte range; applies mutators; checks each mutant with the oracle and the reference extractor; writes the mutants as a corpus of their own |

## Sources

Every valid (non-negative) `ledger` or `xdr` entry of the corpus up to `--max-bytes`, and, cut out of each ledger
at their typed byte ranges, its first transaction envelopes and `SCVal`s, so the value decoders of every SDK see
real values of those types too.

## Mutators

| Class | Mutators | The oracle |
|---|---|---|
| 2, metamorphic | `change-permute` (each operation's change list reordered across ledger keys only: every change of one key keeps its relative order, and a `STATE` or `RESTORED` change stays next to the `UPDATED` or `REMOVED` change of the same entry), `timing` (the `core_metrics` timing values zeroed or altered) | must accept, and the reference extractor's facts must equal the original's |
| 3, wire-invalid | `bool-2`, `opt-flag-2`, `padding-nonzero`, `disc-unknown`, `enum-range`, `len-over-remaining`, `len-over-max`, `truncate`, `trailing`, each written at the byte offset of a typed value | must refuse |

A valid-preserving mutant of a ledger has its dependent hashes recomputed (transaction hashes in the results,
the transaction set hash, the result set hash, the header hash; the SCP signature cannot be redone without the
validator's key); `--stale-hashes` leaves them as they were. The ledger's own protocol version and sequence
number are not mutated. A mutant may stack up to three valid-preserving mutations; candidates are minimised to
one.

The oracle is the pinned `stellar-xdr` decoding strictly and re-encoding byte for byte. Two kinds of value are
XDR-valid but not values stellar-core ever emits, and are marked on the mutant: text that breaks a protocol
character rule (asset codes, symbols, home domains, data names), and ledgers whose parts no longer agree (a
transaction set and processing list that differ, an operation result list that no longer matches its
operations, an updated entry that no longer follows its own state). A reader may refuse those; a reader that
halts on them is still reported, with the rule named.

## Verdicts

Each (mutant, reader) pair ends in exactly one verdict:

| Verdict | Meaning |
|---|---|
| `accepts-invalid` | the reader accepted a mutant the oracle and stellar-core refuse |
| `refuses-valid` | the reader refused, at the XDR level, a mutant the oracle and stellar-core accept |
| `halt` | the reader crashed, timed out, ran out of memory, panicked or stopped ingesting |
| `wrong-fact` | the reader accepted but re-encoded different bytes, or reported facts the oracle does not give |
| `order-dependent` | a metamorphic mutant changed what the reader reports |
| `cross-reader-split` | the oracle and stellar-core disagree on the mutant (it is quarantined as an oracle question), and the SDKs split too; the readers outside the group spanning the most SDKs are in the split |
| `reader-consensus` | every SDK that ran (two families or more) disagrees with the oracle the same way, but stellar-core sides with the oracle: the SDKs share a mistake against the network's reading; reported in a section of its own |
| `conform`, `n_a`, `refused`, `flaky`, `inherited`, `oracle-question`, `reference` | not findings: the reader agrees; the input is beyond the reader's reach; the reader refused a value that breaks a protocol rule, or an object layer refused a protocol-invalid value; flaky; the reader fails the unmutated control the same way; the oracle cannot judge (stellar-core disagrees with it, or every SDK agrees against it and stellar-core did not run); the stellar-core column itself |

Replay adapters see the valid-preserving and metamorphic ledger mutants and their unmutated controls; the
harness serves a ledger by decoding it, so a wire-invalid ledger cannot be delivered to them.

## Triage

A candidate's signature is (reader with its version, verdict, mutator, value type and generalised path). Nothing a run writes lands in the repository.

## Commands

```text
xdrcheck mutate run [--seed N] [--budget N] [--columns all|none|GLOBS] [--adapters all|none|NAMES] [--entries GLOBS]
               [--classes …] [--mutators …] [--max-bytes N] [--stale-hashes] [--no-suppress] [--minimise N]
               [--timeout D] [--memory-max SIZE] [--as-limit SIZE|GLOB=SIZE,…] [--adapter-memory-max SIZE] [--adapter-deadline D]
xdrcheck mutate replay   --entry SOURCE [--variant N] --seed N --mutation IDS [--readers …] [--print READER]
xdrcheck mutate minimise --entry SOURCE [--variant N] --seed N --mutation IDS --reader R [--readers …]
xdrcheck mutate promote  --entry SOURCE [--variant N] --seed N --mutation IDS --id NEW_ID [--into DIR] [--public]
```

`--as-limit` takes one size for every column, or `GLOB=SIZE` pairs per column (for example `rust@*=1G,go@*=1G`):
node-based drivers cannot start under a small address-space cap, so the JS columns are left out of one.

`run` exits 0 when the run is whole (candidates may have been found) and 2 when the kit's own tooling failed (the mutation engine, a driver protocol error, a harness fault) or a cell ended in no known verdict. `--public` writes into the repository's corpus for an ID already planned). `scripts/offline-run.sh xdrcheck mutate run …` runs the whole thing with no network.
