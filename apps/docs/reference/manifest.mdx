## 1. Purpose

One JSON file per **entry**. An entry describes one rare-but-valid (or, for negative entries, deliberately invalid)
pattern of Stellar ledger data: where its bytes came from, which CAP and protocol made it possible, and what a
correct reader must produce from it. The manifest files plus the blobs they point to are the whole corpus. Every
tool of the kit — the oracle, the generator, the replay harness, the conformance runner, the guide generator and
the coverage report — reads these files and nothing else.

Terms used throughout:

| Term | Meaning |
|---|---|
| reader | Any software under test that consumes the bytes: an SDK, an indexer, an ETL pipeline |
| oracle | The kit's decoder, built on the pinned rs-stellar-xdr (`stellar-xdr` crate); it produces the decoded sidecars and runs the checks of [§11](/reference/manifest/checks-and-versioning#11-checks-beyond-the-json-schema) |
| adapter | The component that drives one indexer for the replay harness and reports what the indexer stored as *observations* (`corpus/schema/adapter-protocol.schema.json`, `corpus/schema/observation.schema.json`) |
| driver | The component that runs one SDK version for the conformance runner (`corpus/schema/driver-protocol.schema.json`) |
| consumer | Anything that compares a reader's output with an entry: the replay harness's matcher, a conformance driver, the reference extractor |

### 1.1 Where the core facts live

Six facts identify every entry: its ID, CAP, protocol version, source, whether it is synthetic, and its expected
decoded values. They map onto the manifest like this:

| Fact | Manifest field(s) | Notes |
|---|---|---|
| entry ID | `id` | Stable, never reused ([§5](/reference/manifest/entry-fields#5-entry-ids)) |
| CAP | `caps` (and `caps_note` when empty) | CAP numbers as integers. A pattern no CAP introduced carries `caps: []` and a `caps_note` saying why, by design ([§4.1](/reference/manifest/entry-fields#4-1-top-level)) |
| protocol version | `protocol.introduced`, `variants[].protocol`, `variants[].header_protocol` | Three different facts that one number would blur: the first protocol that can emit the pattern; the protocol applied when these bytes were emitted; and, on upgrade ledgers, the header's protocol, which differs from the applied one ([§4.2](/reference/manifest/entry-fields#4-2-variants)) |
| source | `variants[].source` | One of five typed provenance records ([§4.4](/reference/manifest/entry-fields#4-4-source-six-kinds)) |
| synthetic flag | `synthetic` | `true` only for bytes stellar-core did not emit |
| expected decoded values | `variants[].decoded` (the full decoded rendering) and `expect` (semantic facts and pinpointed values) | Three layers ([§6.1](/reference/manifest/expected-values#6-1-three-layers)) |

### 1.2 The worked examples

Three entries in `corpus/manifest/` are the worked examples quoted in this document (the corpus holds many more; `corpus/COVERAGE.md` lists them by CAP):

| Entry | Source | Shows |
|---|---|---|
| `cap-0040/signed-payload-signer-added` | one public testnet ledger (`history`) | a lake object and its blob; a signer compared in full; a whole-ledger transaction list; two indexer known divergences |
| `cap-0038/pool-issuers-order-by-bytes-not-strkey` | one public testnet ledger (`history`) | a focus that is not the first transaction; pinpoints into the transaction set; known divergences in four SDK families |
| `cap-0073/sac-trust-creates-trustline` | local stellar-core runs (`local-core`), four variants | shared `expect` with per-variant `derived` values; `only_if`; a chain index; a recorded golden mirror run |

## The smallest manifest file

`corpus/manifest/strkey/non-ascii-lookalike-and-case.padded.json` is the smallest manifest file in the corpus: an entry of kind `strkey`, which has no `variants`. This is the whole file:

```json
{
  "schema": "xcc.manifest.entry/v1",
  "id": "strkey/non-ascii-lookalike-and-case.padded",
  "title": "G-address with a trailing base32 padding character",
  "kind": "strkey",
  "caps": [],
  "caps_note": "A pure encoding rule: SEP-0023 strkey text for a key type that no CAP in this entry's family introduced; the strkey group is cross-cutting",
  "protocol": {
    "introduced": 1
  },
  "synthetic": true,
  "negative": true,
  "validity": "malformed",
  "flags": [
    "strkey-padding"
  ],
  "shapes": [
    "strkey-account",
    "strkey-malformed-text",
    "strkey-invalid"
  ],
  "why": "SEP-0023 forbids base32 padding; a decoder built on a padding-tolerant base32 library accepts the string, so two strings name one account.",
  "strkey": {
    "text": "GA7QYNF7SOWQ3GLR2BGMZEHXAVIRZA4KVWLTJJFC7MGXUA74P7UJVSGZ=",
    "type": "account",
    "origin": "synthetic (probe vector 9S8)"
  },
  "expect": {
    "reject": {
      "reason": "strkey_padding"
    }
  },
  "conformance": {
    "levels": [
      "L4"
    ]
  },
  "related": [
    "https://github.com/stellar/stellar-protocol/blob/f2d364902615af726b3533021403c8b225aa6e5d/ecosystem/sep-0023.md"
  ],
  "notes": "Built by xdrcheck-corpus synth from corpus/recipes/strkey/non-ascii-lookalike-and-case.padded.json. Executed in every probe column as vector 9S8 (evidence/sdk-matrix/vectors/vectors.json).",
  "reference": "spec"
}
```

Its fields are specified in [§4.1](/reference/manifest/entry-fields#4-1-top-level), [§9.2](/reference/manifest/kinds-and-levels#9-2-strkey) and [§9.3](/reference/manifest/kinds-and-levels#9-3-negative-entries). An entry of kind `ledger` or `xdr` adds `variants`, the bytes per network and protocol ([§4.2](/reference/manifest/entry-fields#4-2-variants)), each with a `source` ([§4.4](/reference/manifest/entry-fields#4-4-source-six-kinds)); every entry states its expected facts under `expect` ([§6](/reference/manifest/expected-values#6-expected-values-and-how-they-are-matched)). [Read an entry](/start/read-an-entry) walks one such entry field by field.
