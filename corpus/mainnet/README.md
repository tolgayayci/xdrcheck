# Mainnet tier: real pubnet transactions that hold every transaction-level shape token

The mainnet tier is a list of 6,158 pubnet transactions from 6,150 ledgers. Each one is located in its object in
the public Stellar data lake. Their bytes are not committed here. `make mainnet-fetch` fetches them into a cache,
and `make verify-mainnet` checks the tier from that cache.

| File | Content |
|---|---|
| `tier.json` | the header: network, lake store, scan range, token grammar, counts, the sha256 of `tier.jsonl` (schema `corpus/schema/mainnet-tier.schema.json`) |
| `tier.jsonl` | one line per transaction, in cover order (schema `corpus/schema/mainnet-tx.schema.json`) |

## What is claimed

**Every transaction-level shape token that occurs in pubnet ledgers 2 to 65,505,999, as the public data lake
serves them, occurs in at least one transaction of this tier.** That is 15,186 tokens.

A **token** is defined exactly as in `evidence/mainnet-scan/README.md`: one string `<kind>|<class>|<body>` of the
grammar `xcc.shape/v1` (`crates/xdrcheck-corpus/src/cmd/scan/shape.rs`). Its id is the first 16 bytes of
sha256("xcc.token/v1\n" + token), the same id the scan's token cover uses. A token is **transaction-level** when it
occurs in a transaction-level component somewhere in the scan: `E`, `A`, `O`, `R`, `F` or `M`. The scan counted
15,186 such tokens (`evidence/mainnet-scan/cover-summary.tsv`, row `TOK`, column `ids_tx`), out of 15,884 tokens in
all.

The claim has two halves, and they rest on different evidence:

- **That the tier holds these 15,186 tokens is checked here.** `make verify-mainnet` checks it from the lake
  objects (see below).
- **That these 15,186 are all the transaction-level tokens in the range rests on the scan.** That is the scan of
  every ledger in the range described in `evidence/mainnet-scan/README.md`. The tier is that scan's rare-first token
  cover (`cover-summary.tsv`, row `TOK rare`: 6,158 transactions in 6,150 ledgers). The scan's per-ledger output and
  its token table are not in this repository.

## What is not claimed

- **Not "every token mainnet ever produced."** The lake's older ledgers were regenerated by a recent stellar-core,
  so their meta is in a recent version. A shape that only older stellar-core versions wrote is not in the scan. The
  range also ends before protocol 30.
- **Not the ledger-level tokens.** These are the tokens of the component `L`: header, upgrades and transaction-set
  structure. 698 tokens occur only there, and they are out of this tier's scope.
- **Not whole-transaction shapes or component shapes.** The tier covers tokens: each token occurs somewhere in the
  tier. It does not hold every combination of tokens that mainnet produced (`evidence/mainnet-scan/README.md` counts
  those).
- **Not results.** The tier reports no SDK, conformance or pipeline results: nothing here says what any reader does
  with these transactions.
- **No CAP tags.** The tier does not map tokens to CAPs. A reliable mapping needs a table from XDR types to CAPs,
  which does not exist yet, and a guessed tag would read as a fact.

## A line

```json
{"ledger":851123,"tx_index":0,"tx_hash":"…","protocol":1,"lcm_version":0,
 "lake_key":"FFF34DFF--832000-895999/FFF3034C--851123.xdr.zst","object_sha256":"…","object_bytes":709,"blob_offset":12,
 "parts":[["env","TransactionEnvelope","/v0/tx_set/txs/0",400,228,"…"], …],
 "tokens":["…", …],"rarity":1}
```

- `ledger`, `tx_index`, `tx_hash`, `protocol`, `lcm_version`
  - `tx_index` is the apply order: the index into the ledger's `tx_processing`.
  - `protocol` is the header's protocol version.
  - `lcm_version` is the `LedgerCloseMeta` arm.
- `lake_key`, `object_sha256`, `object_bytes`
  - The object's key under the store in `tier.json` (`s3://aws-public-blockchain/v1.1/stellar/ledgers/pubnet`;
    over HTTPS at `https://aws-public-blockchain.s3.us-east-2.amazonaws.com/v1.1/stellar/ledgers/pubnet/<key>`).
  - The sha256 and size of the object, compressed, as the lake served it.
- `blob_offset`: where the ledger's `LedgerCloseMeta` starts in the decompressed object.
- `parts`: the transaction cut as `xdrcheck-corpus scan cut-slices` cuts it. The parts are the envelope, the result
  pair, the meta, and one `LedgerEntryChange` per fee change and per post-apply fee change. Each part is given as
  name, XDR type, JSON path in the ledger, byte offset in the `LedgerCloseMeta`, length and sha256.
- `tokens`: the ids of the tokens that this transaction holds and that no earlier line holds, sorted.
  - The lines follow the cover's order: the rarest token's occurrence, then ledger, then transaction shape id at
    level G3, then the first apply index of that shape in the ledger.
  - So every listed token is on exactly one line, and the lines' token lists together are the 15,186.
- `rarity`: how often the transaction's rarest token occurs in the scan's token table.
  - That count is the sum, over the distinct components that carry the token, of the transactions holding each
    component.
  - So it is an **upper bound** on the number of pubnet transactions in the range that carry the token: a
    transaction with two components that carry it counts twice.
  - 1 means that one transaction in the range carries it.

## Fetch and check

```sh
make mainnet-fetch        # network: the 6,150 lake objects (about 1 GB) into $XDRCHECK_CACHE/mainnet/objects/
make verify-mainnet       # from the cache only; OFFLINE=1 runs it with the network cut
```

**`xdrcheck-corpus mainnet fetch`** (`make mainnet-fetch`):

- Fetches each object with a plain HTTPS GET, at most `--jobs` at a time.
- Keeps an object only when its sha256 and size are the line's.
- Skips an object that is already in the cache with the right hash, so a rerun resumes where it stopped and a full
  cache needs no network.
- If the lake serves an object with other bytes, keeps it beside the cache as `<key>.drift` and reports it as drift.
  The run then fails.

**`xdrcheck-corpus mainnet check`** (`make verify-mainnet`) reads only the cache and fails on any mismatch. For every
line it checks:

1. the object's sha256 and size;
2. its decompression, and the batch split with the byte-exact re-encode of the ledger;
3. that the ledger sits at `blob_offset`;
4. for each part, that the bytes at its offset have its sha256 and round-trip byte for byte through rs-stellar-xdr as
   its type;
5. that cutting the transaction again with the code of `scan cut-slices` gives exactly the line's parts;
6. the transaction hash under the pubnet passphrase, the header protocol and the `LedgerCloseMeta` arm.

It then walks every ledger with the scan's own emitter (the cut into components of `scan run`, grammar
`xcc.shape/v1`), and checks that:

- each line's tokens are exactly the transaction's tokens that no earlier line holds;
- the union of the lines' tokens is the header's count (15,186);
- the union of every walked transaction's tokens is that same count.

`scripts/py/check_mainnet_tier.py` (in `make repo-checks`) checks the two files without the objects:

- the schemas;
- the header's sha256 and counts;
- one line per transaction, and each token on exactly one line;
- the lake keys and the cover order.

## How the tier was made

```sh
xdrcheck-corpus mainnet build --cover cover-TOK-tx-rare.tsv.zst --token-table tokens.tsv --objects <lake objects>
```

- **Inputs.** The scan's rare-first token cover (`scan cover-stream`; one row per transaction: ledger, apply index,
  count of new tokens, rarest occurrence) and its token table (`scan token-census`). Neither is in this repository.
- **The walk.** `build` walks every object with the same code as `check`.
- **The order.** It recomputes the cover's order key, and from it the tokens each transaction newly covers.
- **The guard.** It writes nothing unless every row's count of new tokens and rarest occurrence equal the cover's,
  and unless the union is every transaction-level token of the table.
