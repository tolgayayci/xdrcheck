# guide

Source of the indexer-hardening guide, written for developers.stellar.org (Mintlify).

| File | What it is |
| --- | --- |
| `indexer-hardening.mdx` | The main page: validated versus unvalidated fields, caps, participants from meta, muxed and signed-payload handling. Proposed location in the docs repository: `docs/data/indexers/build-your-own/indexer-hardening.mdx`. |
| `VERIFICATION.md` | The authors' verification report: how each claim was checked, with which evidence, and what is still open. Generated by `review/build.py` from `review/verification.template.md`; not a review. |
| `claims.yaml` | One record per normative statement, with its source (code at a pinned commit, CAP or SEP section, corpus entry or executed probe), its verification and its review status. Schema: `corpus/schema/claims.schema.json`. |

The field-by-field table is not written by hand. The page holds one marker pair per group
(`{/* BEGIN GENERATED: fields envelope */}` … `{/* END GENERATED */}`); the table is generated into
them from `corpus/fields.yaml` joined with the corpus manifest.

## Writing rules

- Every normative statement carries a claim tag right after it: `sentence. {/* claim: C-6101 */}`.
  A sentence containing "must", "never", "should" or "do not" without a tag fails the check. A table
  row is one statement; a tag anywhere in the row covers it.
- Add the claim to `claims.yaml` with the same `sentence` (links reduced to their text, bold removed,
  table cells joined with ` | `) and the enclosing section's anchor as `guide_anchor`. Facts are
  `kind: fact`, advice is `kind: recommendation`. New claims start as `reviewer_status: unreviewed`.
- Every number says its unit and whether it was measured, derived, or read from code or XDR.
- Caps advice for readers of ledger meta is "at or above what stellar-core admits, bounded by input
  length"; never a fixed low cap. What to do at a bound is a declared trade-off, not a rule.
- Name corpus entries by canonical ID (`corpus/plan.json`), in backticks.
- Docs style: CAP-40 and SEP-23 without zero padding in prose, root-relative internal links without a
  file extension, built-in components only, a blank line inside every component tag, body starting
  at `##`. The page names no internal working file.

## Checks

```sh
.venv/bin/python scripts/py/check_fields.py         # fields.yaml and claims.yaml
.venv/bin/python scripts/py/check_guide_claims.py   # the page against claims.yaml
.venv/bin/python scripts/py/check_guide_entries.py  # every cited corpus entry exists in corpus/index.json
```

The first two run in `make repo-checks`; the third runs inside `guide/review/build.py --check`. `make verify-guide` also runs the generators' `--check` modes and the docs
repository's own checks (`pnpm format:mdx`, `pnpm check`, `pnpm check:links`) in a clone of stellar-docs at the
pinned commit (`scripts/docs-check.sh`; `make fetch` caches it, so it runs offline).

## Files

- `indexer-hardening.mdx` — the main page; its field tables are generated from `corpus/fields.yaml` and the manifest.
- `checklist.mdx` — the checklist, generated from the linter's rule registry (`lint/cmd/xdrlint-docs`); it is
  linked from the main page and from the navigation patch.
- `generated/` — the generated blocks embedded in `checklist.mdx`.
- `claims.yaml` — the claim-to-source map for every factual sentence.
- `review/` — the reviewer package (`review/build.py`): claims export, unverified rows, highest-risk claims,
  questions, request draft.
- `VERIFICATION.md` — the authors' verification report, generated by `review/build.py` (its numbers come from the
  files above; `review/code-refs.tsv` records that every cited code line exists at its pinned commit).
- `REVIEW.md` — the handover for the reviewer: what to check first, the claims file format, how a review is recorded.
- `docs-nav.patch` — adds the pages to the stellar-docs navigation.

## Review

Publication waits for a review by a core or platform engineer: every fact claim `confirmed` or
`corrected`, none `disputed`. Each review comment changes the claim's `reviewer_status` and, where
needed, adds a `reviewer_note`.
