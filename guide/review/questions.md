# Questions for the reviewer

These are the points we cannot settle from the code at the pinned commits alone, or where a mistake would mislead
the most readers. Each names the claims (`C-nnnn`, in `claims.csv`) and field-table rows (`VF-nn`) it bears on.
`build.py` checks that every claim and row named here exists.

1. **The field-table verdicts.** Is each "validated", "partially validated" and "passed through" verdict right
   for stellar-core v30.0.0? The rows published on a code reference alone, with no executed demonstration, are
   listed in `unverified.md`; those are the ones we most need checked.
   Rows: VF-01 to VF-53.
2. **Unmatched authorization entries.** We read that an authorization entry no `require_auth` call matches is
   decoded and converted but never authenticated, and that no rule requires every entry, or every delegate, to be
   matched. Is there such a rule anywhere, in the host or in core?
   Rows: VF-48. Claims: C-6131, C-6132, C-6133, C-6134.
3. **Caps and depth units.** Are the decoder stack limit, the envelope admission depth before and from Protocol
   28, the host decode depth and the host value-nesting limit stated correctly, and is the relation we draw
   between the Rust (rs-stellar-xdr) measure and the xdrpp measure right? Which envelope depth did the core
   releases that were live during Protocols 20 to 22 admit? How deep can a tree of authorized sub-invocations be
   in a successful and in a failed transaction?
   Rows: VF-49, VF-50. Claims: C-7013, C-7014, C-7015, C-7016, C-7020, C-7021, C-7022.
4. **An archived-entry index that points at a live entry.** What does core do when an index in
   `archivedSorobanEntries` names a read-write entry that is live, not archived?
   Rows: VF-45.
5. **Clawback with a muxed `from`.** Where does a clawback whose `from` is a muxed account that reduces to the
   issuer fail at apply?
   Rows: VF-20, VF-34. Claims: C-2001, C-3401.
6. **Backfilled meta in the public ledger data set.** Which core version and configuration flags produced the
   Protocol 1 to 22 ledgers that now carry `TransactionMeta` v4 with backfilled events?
   Claims: C-6150.
7. **An explicit void routing ID.** Is "an explicit void `to_muxed_id` means there is no routing ID" the rule
   the ecosystem should follow?
   Claims: C-9012, C-9015.
8. **The signed-payload bound.** Core rejects an empty signed payload and XDR caps it at 64 bytes. Should SEP-23
   state the 1 to 64-byte bound?
   Claims: C-9023.
9. **Events and the emitting contract.** Is it complete to say that a token-shaped event is a movement of a
   classic asset only when its contract ID equals that asset's Stellar Asset Contract ID, and that an account
   named in an event is not a participant unless ledger-entry changes show it was touched?
   Rows: VF-53. Claims: C-6126, C-6127, C-8009, C-8010, C-8011, C-9018.
10. **Non-canonical encodings in meta.** Can ledger meta written by core ever carry a non-canonical XDR encoding,
    such as a boolean encoded as 2 or an undeclared value in a plain enum field? Does core's admission path
    check enum fields?
    Claims: C-6156, C-6160.
11. **Time bounds at apply.** Pubnet ledger 30379767 (Protocol 13) holds a `txTOO_LATE` result with the fee
    charged and, in the meta of the public ledger data set (regenerated by a later core), the sequence number
    unchanged; CAP-34 describes the race as consuming a sequence number. Which is right for the ledgers as
    originally closed? Can a transaction still land with `txTOO_LATE` or `txTOO_EARLY` after CAP-34 (the pubnet scan
    finds no `txTOO_LATE` after the upgrade to Protocol 15)? What is the deepest value nesting core admits in a
    failed transaction's envelope in each protocol era?
    Rows: VF-04, VF-14, VF-50. Claims: C-1432, C-6161, C-6172, C-6173, C-8033.
